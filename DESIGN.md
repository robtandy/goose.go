# `goose.go` Architecture & Design

## 1. Compiler Pipeline Integration

The Goose compiler (`src/main.cpp`) executes six passes over the AST (`src/ast.h`):
1. **Parse** (`src/lexer.h`, `src/parser.h`) -> `Ast`
2. **Resolve** (`src/resolve.h`) -> type aliases & namespaces resolved
3. **Typecheck & Monomorphize** (`src/typecheck*.h`) -> clones one `FnSpec` per live specialization, enforces all reference root, provenance, writability, shrinking, and lifetime rules (§3–§11 of `docs/goose_spec.md`)
4. **Optimize** (`src/optimize*.h`) -> function inlining, constant folding, base-case inlining, tail-recursion elimination, loop strip-mining
5. **Bounds-Check Elimination (BCE)** (`src/bce.h`) -> marks `Index::nobc = true` and `SliceExpr::nobc = true` wherever bounds are statically proven safe, plus loop hoisting (`hoistrefs`, `hoistfields`)
6. **Codegen**:
   - Existing C backend: `src/codegen*.h` (`CodeGen`)
   - **New Go backend**: `src/codegen_go*.h` (`CodeGenGo`), selected via `--target=go` (or automatically when `-o <file>.go` ends in `.go`).

Because `CodeGenGo` runs **after** `TypeCheck`, `Optimizer`, `BCE`, and `BoundStacks` (`src/codegen_stacks.h`), it receives:
- Fully monomorphized `FnSpec`s with exact static stack counts (`fn->numstacks`, `BoundStacks`)
- Already-inlined hot functions (bypassing Go `cmd/compile`'s 80-node inlining budget)
- Proven `nobc` flags on array/slice indexing (allowing `CodeGenGo` to emit raw `unsafe.Add` loads/stores without Go slice bounds checks).

## 2. Pure-Go Data Stack Runtime (`runtime/go/`)

`runtime/go` (the package `github.com/robtandy/goose.go/runtime/go`) is the one copy of the runtime there is (issue #19). The compiler's build embeds the source of its files (`cmake/go_runtime.cmake` writes them into a header, `go_runtime_files`, which `src/codegen_go_runtime.h` reads), every file but `goose_package.go` and `goose_extra.go`, which are the package's alone: what it has as a package of its own (its default sizes, its own program, counts for tests) and functions no file the compiler writes calls. A file the backend writes holds the part of that source its program uses, or all of it, or imports the package (§3.11); the build runs the script again whenever a file changes, so the two cannot drift, and `test/run_go_tests.py` checks that the runtime a compiler embedded is `runtime/go`'s as it is (`goose --emit-go-runtime dir`). So every name the generated code calls is exported there; those a file that holds the runtime keeps to itself are marked `//goose:internal`, which the compiler unexports as it embeds them (`GsEscape` is `gsEscape` in such a file). The files: `goose_runtime.go`, blocks and regions and what a program is to the runtime (`GsProgram`); `goose_bytes.go`, aborts and the operations on values; `goose_format.go`, the text forms print uses; `goose_spans.go`, the freelists of slice pools; `goose_os.go`, the OS layer behind `stdlib/os.goose`; `goose_threads.go`, workers and queues.

### 2.1 Virtual-Memory Data Stacks (`syscall.Mmap`)
- Each Data Stack reserves `GS_STACK_RESERVE` bytes (default 2 GB, configurable) + `GS_STACK_GAP` (1 MB) of anonymous virtual address space via:
  ```go
  syscall.Mmap(-1, 0, reserve+gap, syscall.PROT_READ|syscall.PROT_WRITE, syscall.MAP_ANON|syscall.MAP_PRIVATE)
  ```
- The trailing `GS_STACK_GAP` is marked `syscall.Mprotect(gapSlice, syscall.PROT_NONE)` so runaway stack growth triggers an immediate OS fault at the guard page rather than corrupting memory.
- If the OS refuses a 2 GB reservation (e.g., strict `ulimit -v` or `vm.overcommit_memory=2`), `gs_reserve_region` halves the reservation size down to a minimum of 1 MB, matching C Goose (`src/runtime/runtime_impl.h`): every region from then on is no larger (`gsRegionCap`), whatever it asks for. The first 2 MB of a region are kept out of transparent huge pages on Linux (`MADV_NOHUGEPAGE`), as C's are.
- Physical RAM pages are demand-paged by the OS kernel only as the stack top (`Top`) advances.

### 2.2 Goroutine-Safe `GsStackBlock` & `sync.Pool`
Unlike C threads (`__thread`), Go goroutines multiplex across OS threads and a process may have tens of thousands of idle goroutines.
- Instead of OS thread-local storage, `goose.go` encapsulates a thread/worker program's Data Stacks in a `GsStackBlock`:
  ```go
  type GsStackBlock struct {
      Stks []unsafe.Pointer // current stack tops, indexed by gs_sp + k
      Base []unsafe.Pointer // base addresses of each reserved mmap stack
      Cap  []int64          // reserved byte capacity of each stack
  }
  ```
- Every generated Go function that uses Data Stacks (or calls one that does) takes `(gs *GsStackBlock, gs_sp int64, ...)` as its leading parameters—mirroring C Goose's `int64_t gs_sp` hidden parameter (`docs/implementation.md` §6.2).
- A program is a `GsProgram` to the runtime, which the generated file declares, `gsProg`: the configuration it was compiled with (`StackReserve`, `StackGap`, `FrameReserve`), which every block it makes has, whether it is a library (`Library`), the cap on its workers (`Start`, §2.3) and a `sync.Pool` of `*GsStackBlock` instances, which its exported Go entry points (`export fn`) take a block from (`gsProg.AcquireStackBlock(numStacks)` / `gsProg.ReleaseStackBlock(gs)`) in ~15 ns, run the entire CPU-bound Goose computation with 0 GC allocations, rewind stack tops to `Base`, and return it to. The programs of a process each have their own, however many packages share one runtime (§3.11).
- Callers can also manage a `*GsStackBlock` explicitly (`AcquireStackBlock` / `ReleaseStackBlock`, or `NewStackBlock` / `Reset` / `Close`, the package's, which make blocks of its program's sizes) to keep parsed DOMs or zero-copy structures alive across multiple calls on the Data Stack before rewinding in $O(1)$.
- A block also carries the program instance it runs, in a program with workers (`Gl`, §2.3), and which worker runs on it.

### 2.3 Workers, Queues and Program Instances (`goose_spec.md` §11.2)
`src/codegen_go_threads.h` compiles Goose's concurrency as the C backend does (`codegen_builtins.h`, `runtime_threads.h`, `docs/implementation.md` §6.3, §6.8); the runtime it calls (`go_runtime_threads` in `src/codegen_go_runtime.h`, and `runtime/go/goose_threads.go`) is written into a file that uses it.
- **A worker** is a goroutine running its thread program on a `GsStackBlock` of its own, of its program's sizes, which it reserves as it starts (`gsProg.ThreadSpawn`, `gsThreadMain`): the data stacks its program counts, then the dedicated ones its arguments and globals land on, its fixed-frame stack, its program instance, and a private copy of its spawn packet, which the spawn takes, all outside the Go heap. The goroutine releases all of them (`Close`) before it publishes its end, which is what `thread_wait` waits for; ids increase from 0 and are never reused, and a wait on an unissued id or on the waiting worker itself aborts (`GS_E_THREADID`, `GS_E_THREADSELF`).
- **`thread_spawn`** packs the arguments contiguously on a scratch stack, then each global the worker's program reaches as `[int64 size][image]`, as C's does: a fixed-size value's bytes, a bytes value's image, a resizable's count, a frame object's fixed fields (packed) and its elements, a pool's freelist after its elements. The worker's thunk (`gsTmain_<worker>`) unpacks them onto its block's dedicated stacks and into its instance and runs the body with its stacks from 0; a fixed-size argument of more than 4096 bytes stays in the packet, which the worker owns, as C passes one. `--stacks` reports each worker's stacks and the thread cap as C's does.
- **Aborts.** Every abort panics with a `*GsError`; each thread program's goroutine recovers it. A contained worker (`thread_spawn_contained`) keeps the message of one with a location for the first `thread_wait(id, msg)` that asks, and its waits answer `false`; anything else -- an abort in main or in a worker that is not contained, the runtime's own failures, a fault in a guard gap (`debug.SetPanicOnFault` is set per goroutine) -- ends the process, with one report, from whichever goroutine (`gsEnd`), as `exit(code)` does (`gsProg.Exit`). A library never exits the process, which is its host's (`gsProg.Library`, §3.5): there `exit(code)` panics with a `*GsError` too, and what would end the process stays the panic of its `*GsError`, which an export's caller can recover. On a worker's goroutine, which the runtime started, no host can, and the process ends as it does for any goroutine's unrecovered panic.
- **Program instances.** In a program that spawns workers, every global that is not read-only static data (`CStaticInit`, which every instance shares as it is) is a member of `gsGlobals`, one instance per thread program: main's is the static `gsGlobalsMain`, a worker's the copy its spawn took. A function that names one reads the instance from its block once, `gs_gl := (*gsGlobals)(gs.Gl)`, and so takes the block; a global's dedicated stack is the block's stack its instance names (`gs_gl.gsGStk_<name>`), and the channels of `return ... from` are members too. A program without workers keeps its globals in package variables, at no cost.
- **Queues** are a `GsQueue` per element type, a FIFO of value images (the same images a spawn packs) under a mutex: `qput` copies before it locks and never waits, refusing a put at the queue's limit (`qlimit`, `GS_E_QBOUND` below one); each waiting receiver waits on a channel of its own, so a timed `qget<T>(ms)` waits for a monotonic deadline; a miss yields `T`'s zero value; a value of no bytes is a message of none.
- **`hardware_threads()`** is `runtime.GOMAXPROCS(0)`, capped at the workers `GS_STACK_BUDGET` holds beside the main program, at least one (`gsProg.Start` and `gsProg.HardwareThreads`, as `gs_rt_start` computes it).
- What differs: recursion deeper than a goroutine's stack holds is a fatal error of the Go runtime at 1 GB, where C reports its native stack's overflow as an abort, in a worker as in main (`test/threads/thread_stack_overflow.goose`).

## 3. Value Representations in `--target=go` (`docs/implementation.md` §6.1)

### 3.1 Scalars & Integer Semantics
- `i8`, `i16`, `i32`, `i64` -> `int8`, `int16`, `int32`, `int64`
- `u8`, `u16`, `u32`, `u64` -> `uint8`, `uint16`, `uint32`, `uint64`
- `f32`, `f64` -> `float32`, `float64`
- `bool` -> `bool` (1 byte, 0 or 1 in binary layouts)
- In release mode (`GS_DEBUG == 0`), arithmetic and casts emit native Go operators (`+`, `-`, `*`, casts), with `gs_f2iwrap` for float-to-int wrapping and zero-checked division/Euclidean modulo (`gs_div_*`, `gs_mod_*`).
- In debug mode (`--debug`), arithmetic and narrowing `as` casts call checked helpers (`gs_add_i32`, `gs_range_*`, etc.) that report the `.goose` file and line on overflow.
- A shift masks its count to its type's width in every build, as C's `gs_shl_*` and `gs_shr_*` do (`ShiftX`); a shift by a constant count outside that width is warned of (§3.10).

### 3.2 Fixed-Size Types (`Fixed` Class)
Goose specifies exact byte layouts (`FixedSize`, `LayoutFields` in `src/codegen_types.h`) with `#pragma pack(1)` semantics. `src/codegen_go_types.h` ports them and keeps every fixed-size value in its C layout, byte for byte, its references and slices included:
1. **Naturally Aligned Structs holding no address** (where every field offset in `LayoutFields` already matches Go's natural alignment and total size matches `FixedSize`, such as `struct YyVal { tag: u64, uni: u64 }`):
   - Emitted as a native Go `struct` so field reads/writes are direct `s.tag_g` / `s.uni_g`; `pad` and `pad n` become blank `_ [n]byte` fields, which Go's `==` ignores as Goose's does.
2. **Every other Fixed Struct & Fixed-Mode ADT** (unaligned offsets, no tail padding, or a reference or slice among the fields):
   - Emitted as `type Name_g [FixedSize]byte`, each field read and written in place at its exact byte offset from `LayoutFields`: `*(*uint32)(unsafe.Add(unsafe.Pointer(&s), off))`.
   - On `arm64` and `amd64`, Go's SSA compiler lowers that to a single unaligned load/store instruction (`LDR`/`STR` or `MOV`).
   - A payload-less ADT is its tag, a named `uint8`/`uint16`; any other fixed-mode ADT the bytes of its tag (`TagStore`) and its largest payload, the payloads overlapping behind the tag as C's union. A static-capacity limited array `T[..k]` is its length (`LenStore`) and its `k` slots, as a native struct where Go aligns the slots and they hold no address, and as bytes otherwise; a fixed array `T[k]` is a Go array.
3. **References and slices.** A plain or optional reference is a typed Go pointer (`*T`, `nil` for null) and a slice a `GsSlice { Data unsafe.Pointer, Len int64 }`; a reference to a value whose Go type itself holds Go pointers (a slice, an array of references) is its `unsafe.Pointer` address. Every address a program holds points outside the Go heap and never moves: into a data stack, into the fixed-frame stack (§3.6), into a global or into a literal's static data. So a value's bytes can hold one where the collector does not look, which needs no write barrier either. A value of a Go type holding Go pointers at an address that may be unaligned (a slice at byte 1 of a struct's bytes, a reference packed on a data stack) is read and written through a copy of its bytes, `gsLd_<T>`/`gsSt_<T>` (`*(*[16]byte)(unsafe.Pointer(&v)) = *(*[16]byte)(p)`), which has alignment 1: `checkptr` accepts it where a typed access would be a misaligned pointer conversion. A self-relative reference is the signed offset C stores, at its width, from the offset C gives its field.
4. **Equality** (`==`, §4.5) is Go's own `==` wherever that is the structural one (native structs of scalars, the bytes of a value whose bytes are its equality, references and slices, arrays of them, tags), and a generated `gsEq_<T>` elsewhere, which compares a limited array's live elements and an ADT's live payload only, and floats by value.
5. **Large values.** A fixed-size value of more than 4096 bytes is one the C backend holds on a data stack wherever it is a local or a temporary (`FixedLocal`). Those stacks are counted in the `--stacks` report both backends share, so this version supports such values where it takes the stacks C does: in globals (built in place, counting the one stack C's initializer takes, or none where C makes the global static data), in a recursive cycle's locals (which take none, in the function's frame), and on a data stack where C takes one too (`CodeGenGo::FixedLocal`): a named local, a literal's or a `default()`'s temporary, a queue's value, and a `thread_fn`'s argument, which stays in its spawn packet. A parameter or result of one, and its other temporaries, are not supported yet.

### 3.3 Variable-Size Byte Images (`Bytes` Class)
- Represented as `unsafe.Pointer` pointing to the start of the self-describing byte image on a Data Stack.
- Fields after a variable-size field are reached via generated `gs_size_<T>(p unsafe.Pointer) int64` walkers and `unsafe.Add(p, offset)`, identical to C Goose (`FieldPtr`, `SizeX`).
- **An ADT adapted from another type.** Where the checker adapts the result of a call -- a function's, a case function's, a builtin's or a function value's -- or of an inlined body to an ADT it does not arrive as (a variant to its ADT, or an ADT to its other mode, `goose_spec.md` §3.5), the value is built as the type it arrives as and converted, as C builds it (`CodeGenGo::AdtFrom`, `GenAdtAdapted`, after `CodeGen`'s): a variant becoming the variable-mode ADT is built behind the ADT's tag; a fixed-mode ADT becoming the variable-mode one is built in a local and written out as the image of the variant it holds; a variable-mode value becoming the fixed-mode ADT, a reference's pointee included, is built on a temporary stack, taken before the call as C takes it, and read from there. A result a return forwards is adapted at the function's destination for it the same way (`GenForward`). Each call is made once, and both backends take the same stacks. A fixed-size value holding relative references adapted so is not supported yet.

### 3.4 Resizable Data-Stack Values (`Resizable` Class) & Slices
- **Slices (`T[:]`)**:
  ```go
  type GsSlice struct {
      Data unsafe.Pointer
      Len  int64
  }
  ```
  (with zero-copy conversion helpers to/from Go `[]T`, `[]byte`, and `string` via `unsafe.Slice` and `unsafe.String`). `a[lo..hi]` is `GsSub(data, lo, hi, n, esize)` once its bounds are checked: the address of element `lo`, an empty slice's too, so that empty slices at different places are different slices as members of a compared composite, as C's are (`goose_spec.md` §4.5), but for one at the end of the run (`lo == n`: `s[s.len..]`, `s[s.len..s.len]`), whose address in C is one past the run's last byte. The run may be an export fn's argument that ends where its allocation on Go's heap does, and an address one past that is no valid Go pointer: `-d=checkptr`, which `-race` turns on, aborts on one, and Go's collector may take one for a bad pointer into its heap (issue #39). Such a slice starts at a word of the runtime's own instead (`gsSubEnd`, outside Go's heap), where no slice of the run, nor the nil one, starts, so that it still differs from all of them; every such slice starts there, as Go's zero-size allocations all start at one address.
- **Resizable Headers (`GsRhdr`)**:
  ```go
  type GsRhdr struct {
      Base unsafe.Pointer
      Len  int64
  }
  ```
  Elements live contiguously on `gs.Stks[gs_sp + k]`. Pushing an element writes `*(*T)(gs.Stks[stk]) = elem` and advances `gs.Stks[stk] = unsafe.Add(gs.Stks[stk], sizeof_T)` + `hdr.Len++`.
- **Fat References (`GsRref`) & Pool References (`GsPref`)**:
  ```go
  type GsRref struct {
      Hdr *GsRhdr
      Stk int64
  }
  type GsPref struct {
      Hdr     *GsRhdr
      Stk     int64
      FreeHdr *GsRhdr
      FreeStk int64
  }
  ```

### 3.5 `export fn` and `extern fn` in Go Mode
`src/codegen_go_export.h` holds the foreign boundary.

- **`export fn`.** Every `export fn foo(a: u8[:], x: i64) -> i64` gets two exported Go entry points, named by its C symbol's words capitalized (`parse_json` is `ParseJson`, `export "sym" fn` renames it), and one taking a `const u8[:]` two more:
  1. `func FooWithStack(gs *GsStackBlock, a []byte, x int64) int64` runs it on the data stacks of a block the caller holds (from `NewStackBlock`, or `AcquireStackBlock`), which it gives back as it found them: a caller may keep one block across calls.
  2. `func Foo(a []byte, x int64) int64` takes a block from its program's pool (`gsProg.AcquireStackBlock(n)`, `n` the export's own stack count), calls `FooWithStack`, and rewinds and returns the block (`gsProg.ReleaseStackBlock`) before returning. Once the pool holds a block, a call allocates nothing on Go's heap (`testing.AllocsPerRun == 0`, `test/go/export/`). An export whose code needs no block calls the function directly.
  3. Where a `const u8[:]` parameter makes them generic, `func FooString(...)` and `func FooBytes(...)` (issue #22): `Foo` taking each such parameter as a `string`, and as a `[]byte`, which Go compiles as it compiles the call they make where the function takes no block (below); one whose function takes a block is `Foo`'s own call. A form whose name another export fn's `Name` or `NameWithStack` has is left out (`count` and `count_bytes`), so that adding the forms renamed no program's entry point.

  The parameters are Go's own values, viewed in place with no copy: `u8[:]` is a `[]byte`; `const u8[:]` either a `string` or a `[]byte` (a type parameter `T ~string | ~[]byte`, written so in the signature, which then names nothing of the runtime's); any other `T[:]` a `[]T`, but for `const (const u8[:])[:]`, a `[]string` (below); `T&` a `*T`; a scalar or a fixed-size value its Go type. What a slice or a reference points at must be flat, as in C (`goose_spec.md` §7.10), Go's strings apart: a Go struct holding a slice cannot cross yet, and [`docs/design/go_views.md`](docs/design/go_views.md) designs read-only views of one (issue #30). A `const u8[:]` result is a `[]byte` viewing what the slice does (the arguments, a global, static data): no export's result can view the block's stacks, which Goose's lifetimes keep a result from pointing into, so `Foo` always gives the block back. What the entry points are handed may end up where only the data stacks see it, so they keep it off Go's moving goroutine stacks (`GsEscape`: a caller's buffer is on the heap, or static), and alive until the call returns (`runtime.KeepAlive`): Go keeps a value alive only up to its last use, which may be the call itself, and the collector does not see what a data stack, the fixed-frame stack or the bytes of a value hold (issue #30, `test/go/export/keepalive/`) -- but where the function keeps it in Go's own variables (below). An abort panics with a `*GsError` in the caller's goroutine. `--library` (or `export fn`s and no `fn main()`) makes the file a package with no `func main`, `package goose` unless `--go-package` says otherwise, which starts at the first call of an entry point.
- **Kernels' entry points** (issue #22). A kernel over slices takes no block, and its entry points made the call of its function and nothing else; but `GsEscape`, a branch on a global, the `runtime.KeepAlive` of each argument and, for a `const u8[:]`, the generic `GsBytesOf` put the smallest of them over Go's inlining budget of 80 (`Sum` of a `u32[:]` cost 78 and `SumWithStack` 81, `CountDigits` 85 at its shape, `Axpy` of two slices 116), and `GsEscape` moved a caller's array off its stack, to the heap, an allocation a call. Where every address the function is handed stays in Go's own variables while it runs (`ArgsStayInGo`), the entry points hand Go's slices and pointers on as they are, with neither: Go's escape analysis follows such a variable, its collector sees the pointer in it, and Go moves it with a goroutine's stack. That is so where nothing the export's calls reach, its own body included, can put one anywhere else, or hand it to code that may: none takes the block (no data stack, fixed-frame stack or program instance); none has a value of a type holding an address but a plain or optional reference or a slice of what holds none: no struct holding one (whose Go value is its bytes, which hide it), no array of them, no reference to one; none names a `var` global of a type that can hold one; none hands one to an `extern fn` but those of the runtime that only read it (`gs_find_any`, `gs_find_pair`, `frexp`, os's files); and none takes free variables or returns from another function (§7.9). The analysis is of the export as a whole, and conservative: an export taking a block keeps `GsEscape` though its code may copy no more than the elements (the README's `median`), and cannot be inlined anyway, its pool and its fault scope costing far more. An entry point then costs its function's cost, 57 where Go does not inline the function, and about 10 for each slice it hands on (`Sum` 52, `SumWithStack` 55, `CountDigitsString` 57, `Norm2` of a `const Pt&` 22, `Axpy` 74, the functions 42, 47, 18 and, not inlined, 233): Go inlines it into its caller, and the function with it where that is small, and a function costing between about 70 and 80 keeps its entry point a call, in which it is inlined. The generic `Foo` reads a type parameter's data through its address, `*(*unsafe.Pointer)(unsafe.Pointer(&s))`, which takes a slot of its caller's frame, a store and a load, where `FooString` and `FooBytes` read none (`unsafe.StringData`, `unsafe.SliceData`). A library with globals to initialize checks its start in every entry point (`gsLibStart`), whose slow path's call costs 57 more: there only the smallest inline. `test/go/export/inlining/` checks all of this: `Runner.entry_points` reads `go test -c -gcflags=-m=2` for each export fn an `// entry:` line annotates (`inline`, `no escape`, `escape`), at -O2 and -O0, and compares the code Go makes for arm64 and amd64 of a call of each kernel's entry points (`callSum`) with that of the call of its function written by hand (`directSum`), which must be the same instructions but for the mark of the inlined call; its tests check what each computes, that a caller's array stays on its stack where nothing escapes and moves where the export keeps the slice on a data stack, in a struct or hands it to an `extern fn` (`testing.AllocsPerRun`), and benchmark the calls. On an arm64 Neoverse N1 with Go 1.24, `Sum` of 4 `u32`s takes 4.42 ns, as the call of `sum_g` written by hand does, where it took 5.63 ns (27% more; 41.0 ns where 39.5 at 64 elements, and as much at 1024: `BenchmarkSum`), and `CountDigitsString` of 4 bytes takes 6.0 ns and the generic `CountDigits` 6.8, where `CountDigits` took 7.7 (`BenchmarkCountDigits`). So no form of a direct call is needed: the functions the entry points call (`sum_g`) stay the generated code's own, with no stable names or signatures, and calling one skips a library's start and the block's fault scope.
- **A Go `[]string`** (issue #42). A Go `string` is its data and its length, the two words of a `const u8[:]` (a `GsSlice`), so a `[]string`'s elements are laid out as a `const (const u8[:])[:]`'s, which an export fn's entry points take as a `[]string`, viewed in place: `GsSliceOf(tags)`, or the slice as it is where the function keeps what it is handed in Go's own variables (`ArgsStayInGo`, which takes a slice of `const` slices of what holds no address as it takes a slice of what holds none: the slices it holds are where Go laid them out, as strings, and its collector sees them there). Both depths are `const`, as nothing may write a Go string's bytes (a literal's are in read-only memory) or re-point the strings of a `[]string` a caller lends; another constness is refused, with the type that crosses. The code reads each string's header where it lies, as it reads any slice held in memory (`gsLd_`, which `-d=checkptr` passes); one `GsEscape` keeps the strings' bytes off a goroutine's stack with their array, since Go's heap never points into a stack ([`go_views.md`](docs/design/go_views.md) §6.1), and `runtime.KeepAlive` of the slice keeps them alive through it. No C host has such a value, and the checker's check of an export's boundary, which is C's, refuses every slice of slices ("nested references and slices do not cross"). So for `--target=go` the driver hides the export fns taking a slice of `u8` slices from it while the program is checked (`HideGoExports`, which `src/main.cpp` calls: they are checked as the functions nothing calls are, which is how an export is checked), and checks them itself after (`CheckGoExports`, `GoExportCheck`, `src/codegen_go_export.h`): `TypeCheck::CheckExport`'s checks in its order and with its messages, but for that parameter. [`docs/upstream/go-string-slices.md`](docs/upstream/go-string-slices.md) proposes the option to the checker that would let these go. `test/go/export/string_slices/` checks the entry points of export fns over a `[]string` -- nil, empty and shared strings, a view of one as the result, an index's abort, a caller's array that stays on its stack for a kernel and moves to the heap where the strings go onto a data stack, goroutines calling at once -- with `-d=checkptr`, and under `-race` where cgo builds (`EXPORT_RACE`); `test/go/export/keepalive/` that the strings of a `[]string` kept on a data stack stay alive while the collector runs; `test/go/export/inlining/` that Go inlines a kernel's entry points over one, which let no `[]string` escape; and `run_go_tests.py`'s `cli` checks the refusals and their messages.
- **A library's start** (issue #18). The package has no `init`: importing it maps no memory, leaves every goroutine's fault handling alone and runs no initializer, so that a host pays nothing for a library it imports for a path it may never take. The first call of any entry point of any export starts it, once, on the caller's goroutine (`gsLibStart`, a `sync.Once` behind an atomic flag): the runtime (`gsProg.Start`), the package's block, and the globals' initializers on it. A library with nothing to start -- no global to initialize, no worker to spawn -- has no start at all (issue #19): its entry points call its functions directly. After that a call pays an atomic load for the start, which costs nothing measurable where Go still inlines the entry point into its caller, as it does the smallest (`Twice` of `test/go/export/exports/`); a larger one that Go inlined before no longer fits Go's budget, the start's call to its slow path counting against it, and costs its caller a call. A start that panics -- an initializer's abort, or a fault in a guard gap, which is the overflow's `*GsError` (`GsAbortOf`) -- leaves the globals unusable: that call and every later one panic with what it did. (An `--include` function that an initializer calls cannot call its package's entry points: such a call would wait for the start it is part of.) Nothing a library runs exits the process, which is its host's: `exit(code)` panics with a `*GsError` naming the status, as an abort does (`gsProg.Library`, §2.3). A call that runs on a block (`FooWithStack`, and so `Foo`) turns panic on fault on for itself only, `defer debug.SetPanicOnFault(debug.SetPanicOnFault(true))`, so that a stack that grows into its guard gap panics in the caller's goroutine, which can recover it, where it would otherwise kill the process, and gives the caller's setting back as it returns or panics; an export whose code takes no block cannot fault so and leaves the setting alone. That costs a call about 5 ns on an arm64 Neoverse N1 with Go 1.24 (`BenchmarkFaultScope` against `BenchmarkNoScope` in `test/go/export/lazy/`: 7.3 ns and 2.1 ns), the deferred call being made through a closure Go builds for its argument: `ChecksumWithStack(gs, "ab")` of `test/go/export/exports/` takes 23.5 ns where it took 18.1, `Checksum("ab")` 58 ns where it took 51, and `JsonSumWithStack` 751 ns as it did. A library's blocks reserve 64 MB of fixed-frame stack each where a program's reserve 1 GB (§3.6).
- **Concurrency.** Each call of `Foo` runs on a block of its own, so goroutines may call exports at once; making blocks is goroutine-safe, and a pooled block the collector drops is closed. In a program without workers, Goose's globals are the package's, shared by every call, as are `return ... from`'s channels: an export that writes a global is not safe to call from two goroutines at once. An export whose calls reach a global that lives on a data stack of its own (growing it, or handing on a reference to it) is refused at compile time, since that stack is in the program's block, not the caller's.
- **Concurrency with workers.** In a program with workers (§2.3), a call runs on a program instance of its block's own, so no two goroutines share a global, as no two Goose threads do. `FooWithStack(gs, ...)` gives a block that has none a copy of the package's instance (`gsEnter`: main's, which the library's start or `fn main()` leaves), the values on data stacks onto the block's own dedicated stacks at the main program's indices; the block keeps it, and what its calls write, until `Reset` or `Close`. `Foo(...)` copies the globals its calls reach into the pooled block for the call (`gsEnter_<fn>`), so it always starts from the package's, and hands back a result viewing them as a copy on Go's heap (`GsKeep`), its block going back to the pool. Such an export may grow a global's stack, which is its block's; one whose calls reach a global holding a reference into a data stack is refused. The queues are the process's, one per element type, shared by every instance (§11.2).
- **`extern fn`.** A call calls the Go function its C symbol names, directly. The C runtime's functions that std, math and os bind are the Go runtime's (`gs_find_any` is `GsFindAny`, `gs_os_read_file` `GsOsReadFile`; the OS layer behind `stdlib/os.goose` is written into a file that calls it), and the C library's that Go's `math` has are those (`floor`, `sinf`, ...; `mul_add` is `math.FMA`, rounded once, as C's is on arm64). Any other symbol is a Go function of the generated file's package, from an `--include helper.go` (or a file beside the generated one): scalars are Go's types, a fixed-size value its generated type (`Pt_g`), a plain reference a pointer to it, a slice a `GsSlice` (`GsSliceToBytes`, `GsSliceToString` view it), and a `u8[>..]&` builder a `GsRref`, after the block, which such a function is handed first to append with (`GsBldAppend(gs, b, data)`, `GsBldAppendString`). It may not shrink the builder or keep what it is handed past the call.
- **`--include helper.go`** is Go source spliced into the file: its package clause and build constraints are dropped, its imports join the file's own, and the rest follows the program, each run of its lines between blank ones under a `//line helper.go:N` directive naming the run's line (`GoIncludeLines`), so Go's errors in it and its panics' frames name its own lines whatever `gofmt` makes of the blank lines between the runs. A run that opens with a declaration's doc comment takes its directive at the comment's end, after an empty comment line, where `gofmt` keeps a directive in a doc comment.

### 3.6 The Fixed-Frame Stack (`gs.Frame`)
A Goose local whose address the program never takes is a Go local, which Go keeps in registers. One whose address it does take (`&x`, `x[..]`, a by-reference argument, a field access of a value held as bytes) cannot be: Go may move its goroutine's stack while the bytes of a value, a data stack or a frame hold its address, and the collector scans none of those. Each `GsStackBlock` therefore has one more `mmap` region, the fixed-frame stack: a function holding such locals (or parameters) takes its frame there as it starts, `gs_fr := gs.Frame; gs.Frame = unsafe.Add(gs_fr, gs_fo<n>)`, each local a pointer to its slot, and gives the frame back at every return and where its body's end is reached. Fixed-size locals never grow, so the frames obey a strict call discipline, recursion included, and a local declared in a loop has the same slot every iteration, as C's does. Each slot is 8-aligned and at least a byte, so that two variables never share an address, a zero-length array's or a payload-less variant's included. `FinishBody` (`src/codegen_go_emit.h`) finds those locals once a body is generated and rewrites their declarations and uses; whether a function then takes the block is settled once every body is (`ResolveGsArgs`). The region's reservation is address space only: 1 GB in a program, the most Go grows a goroutine's stack to, and 64 MB in a library, whose calls' frames C would run on its host's native stack, 8 MB by default on Linux (`--frame-reserve` sets either, as `gsFrameReserve`). A frame that does not fit is reported as C reports its native stack's overflow.

Indexing a fixed array takes no address of it (issue #23). An element of a fixed array that is a Go local's own -- a local's, a parameter's, a temporary's, or a part of one that no pointer leads to, such as a field of a native struct or an element of an outer array (`GoLoc::golocal`) -- is Go's own index expression, `r_g[i]`, its index checked by `GsIdx` or proven in range by BCE (Go's own check then always passes, and Go removes it where it can prove it too, as it can past `GsIdx`, §3.13), and its bytes are sliced where a wide load or store takes them (§3.8). So a `u8[8]` that a function fills and reads a byte at a time, in a loop or not, stays a Go array in registers or on Go's stack, and the function needs no frame, nor the block for one; only a use of its address -- a reference to it or to an element, a slice of it, a by-reference argument, printing it -- still moves it into the frame. An assignment to an element pins nothing: the place is the same wherever it is evaluated, and only its bounds check, where it has one, runs before the right side does (`PinLoc`).

Nor does handing a local to an inlined function by reference (issue #24). A function inlined into its caller -- an `inline fn`, or any small helper the optimizer inlines -- binds each `T&` parameter to its argument at the start of its body, where a call would pass the address. A parameter bound so to a place of a Go local's own (a local, a parameter, a field or an element of one: `GoLoc::golocal`) is that place, and no Go variable (`BindRefPlace`): the body reads and writes `tag_g` where it read and wrote `(*tag_g_2)` through `var tag_g_2 *uint64 = &tag_g`, which made `tag_g` a slot of the frame. Its reference value is the place's address as `RefOfLoc` spells it, `&tag_g`, and every dereference of a reference value looks that text up (`RefPlace`: `DerefLoc`, `CoerceVal`, `AtRef`), so that it is the place again wherever the body dereferences it, a parameter handed on to another inlined body included. The place's bounds check, where it has one, runs where the argument is bound, as the binding's would (`_ = a_g[GsIdx(t5, 4, ...)]`), whether the body reads the reference or not; its index is a snapshot, so the place stays the element it was bound to whatever the variable that indexed it holds later. Only a use of the reference as a value spells the address -- handing it to a call that stays a call, storing it in a variable or a field, returning it, comparing its identity, slicing the place -- and those locals alone move into the frame, as every local handed by reference did. A parameter a nested function reaches (which takes the address of the parameter itself), one a `var` may rebind, an optional one, and one bound to anything but such a place (a global, a pointee, a value on a data stack, a construct choosing one of several) are the Go pointer they were. The parser-shaped loop of `test/go/export/inline_refs/`, six scalars of state that one inlined helper takes by reference a byte at a time, scans 4 KB of JSON-like text in 15.1 µs on an arm64 Neoverse N1 with Go 1.24 (`BenchmarkScan`, 283 MB/s), where it took 19.8 µs with the six in the frame (217 MB/s); the same loop written in Go takes 15.7 µs (`BenchmarkScanGo`), and the issue's `inline fn bump(x: i64&) { x += 1; }` in a loop of 1000 takes 0.51 µs where it took 2.28 (`BenchmarkBumps`). A function whose frame held nothing else no longer takes the block for one (`ResolveGsArgs`).

### 3.7 The Layout: `gofmt`'s
A generated file is laid out as `gofmt` lays it out, so that `gofmt -l` finds nothing to change in it (`src/codegen_go_format.h`). The runtime's text is `gofmt`'s already, and the imports are one group in `gofmt`'s order. The program's Go is written a statement or a declaration to a line with `gofmt`'s indentation, and `GoFormat` lays the finished text out as `go/printer` prints the same Go: it parses each line's expressions as `go/parser` does and spaces each binary operator as `go/printer` does, from the depth and the precedences around it (`a + b` at a statement's top, `f(a+b, c)`, `x[i+1]`, `a*b + c`), which is not known where an expression is generated, inside out; leaves out the parentheses `gofmt` does not print (the outer of two pairs, those around a control clause's expression); aligns the fields of a struct, the specs of a `const` or `var` group and the comments ending consecutive lines in `text/tabwriter`'s columns; and keeps one blank line where `gofmt` keeps one, adding the one it puts before a comment or a declaration of another kind at the package level. `--go-build 'expr'` starts the file with `//go:build expr`, the expression checked and written as `gofmt` writes it (`GoBuildConstraint`), and a blank line. An export fn's Go documentation is its Goose documentation's text as one paragraph, which `go/doc/comment` leaves as it is.

### 3.8 Wide Loads and Stores (issue #23)
The usual way to read a little-endian word from bytes is to OR them together, each shifted to its place, and to write one, to take it apart a byte at a time:
```goose
let c = s[i..i + 8];
let w = c[0] | (c[1] as u64) << 8 | (c[2] as u64) << 16 | (c[3] as u64) << 24 |
    (c[4] as u64) << 32 | (c[5] as u64) << 40 | (c[6] as u64) << 48 | (c[7] as u64) << 56;
for k in 8 { o[j + k] = (w >> (8 * k)) as! u8; }
```
A C compiler makes each of these one load or one store. Go's makes one only where every byte's address is a constant away from one base it knows is no nil pointer -- a byte read through the slice's own pointer, at offset 0, keeps the rest apart with its nil check -- and never of a loop, so `src/codegen_go_wide.h` recognizes them and writes each as `encoding/binary` would: `binary.LittleEndian.Uint64((*[8]byte)(p)[:])`, `binary.BigEndian.PutUint32((*[4]byte)(p)[:], v)`, or for a Go local's own array (§3.6) `binary.LittleEndian.Uint64(r_g[0:8])`. Go compiles that to one load or store, with a byte swap for the other order, on arm64, amd64 and every other target with unaligned accesses, and to the bytes elsewhere: the value is the same on every target, its byte order included, and the conversion to an array pointer has no check but for nil, where `unsafe.Slice` would check that the address cannot overflow on every load. Recognized are:
- **Loads**: an OR of 2, 4 or 8 bytes, each `a[e + c]` widened (`as T`, or implicitly) and shifted left by a constant, at consecutive constants `c` of one array or slice `a` and one index `e` (or at constant indices), each byte shifted to its place in a little-endian or a big-endian order, the leaves in any order or grouping, at any integer type of enough bits; an OR at a wider type is the load zero-extended (`c[0] | (c[1] as u64) << 8` is a 2-byte load into a `u64`).
- **Stores**: `for k in n { o[e + k] = (v >> (8 * k)) as! u8; }` (or `0..n`, `k << 3`, and the big-endian `8 * (n - 1 - k)`, `56 - 8 * k`), and a run of n statements `o[e + c] = (v >> s) as! u8` storing every byte once, in either order, n being 2, 4 or 8, the low n bytes of a `v` of at least as many.

Only where nothing could tell the difference: every byte's bounds check is gone already (`Index::nobc`, or a constant index within a fixed array), so that no check in between could abort; the array is one path that nothing between could move (no call anywhere); the index's arithmetic is 64-bit, where a constant added to an index in range cannot wrap to another one in range (`255 + 1` as a `u8` is 0); every type a byte's value passes through holds it whole, as a zero extension does (an unsigned one of enough bits, or the result's own); and a store's value and index are scalar variables and constants, which the bytes it writes cannot change, its conversion to `u8` one that truncates (`as!`, `as` in a release build, or a value masked to 255 first). The leftmost byte's index is evaluated, as the program would evaluate it first. Anything else is left as it is written, a byte at a time.

The recommended pattern, then, is to prove the span once and to write the bytes out: a slice of the span, `let c = s[i..i + 8];`, and constant indices into it; or a guard BCE can use whatever `i` is, `if i < 0 || i > s.len - 8 { ... }`, and `s[i + c]` (`i + 8 > s.len` is no guard of an arbitrary `i`, since `i + 8` can wrap); or a loop whose condition bounds the index, `while i <= s.len - 8 { ...; i += 8; }`. No `extern fn` doing `binary.LittleEndian.Uint64` is needed, and the C backend gets its one load from the C compiler the same way. `test/go/programs/wide_bytes.goose` (and its `--debug` twin) reads and writes every width in both orders at every offset of slices of every length up to 20, the last bytes included, in each recognized form and in forms left alone, against values worked out a byte at a time; `test/go/export/wide/` compares the loads and stores of export fns with `encoding/binary`'s, and `run_go_tests.py` reads the code Go makes of each for arm64 and amd64: one load or one store (`Runner.wide_asm`). On an arm64 Neoverse N1 with Go 1.24, summing the little-endian words of 4 KB takes 0.43 µs written so (`BenchmarkSumLe64`, 9.6 GB/s), 1.6 µs with `+` in the place of `|`, which is no OR of bytes and stays a byte at a time, and 0.63 µs in Go with `binary.LittleEndian.Uint64(s[j:])`, whose bounds check stays in the loop.

### 3.9 Selects (issue #26)
std's `max` is `if a < b { return b; } return a;`, and inlined, a body is a labeled `switch { default: }` whose every exit assigns the destination. Go makes a conditional select of an `if` (`CSEL` on arm64, `CMOV` on amd64) only where its sides do no more than give an integer local of two bytes or more one of two values: a choice stored into an element is a store on each side, and so a branch; `clamp`'s three exits and `sign`'s are branches; and amd64 has no conditional move of a byte, so a byte's `max` is a branch there. `src/codegen_go_select.h` writes a body that only chooses among values it computes nothing for -- std's `min`, `max`, `clamp`, `abs` and `sign`, inlined or not (a function's own body, at -O0), a function of the program's own written so, as guards, an else-if chain or an if's two returns, and an if choosing between values -- in the shapes Go makes selects of:
- **Go's builtin `min` or `max`** (Go 1.21) of a choice of x or y by a comparison of the two integers, `m = max(a, b)`, whichever of the four orders compares them and whichever way round it picks: equal integers are the same value, so how the comparison breaks a tie does not matter. The destination is assigned once, as a store of one value.
- **Otherwise, a temporary** given the value no condition picks, then each other value under its condition, the first condition last, so that it wins as it did by being tested first; the destination is assigned once, after: `t := x; if hi < x { t = hi }; if x < lo { t = lo }; o[k] = t` is two selects and a store.
- **A byte's choice at four bytes**: `uint8(max(uint32(a), uint32(b)))`, or a `uint32` temporary, where amd64 has a conditional move; extending a byte keeps its order.

Only where nothing could tell the difference: every condition and value is computed whichever value is chosen, so each must be one that nothing in runs a statement or can fail -- scalar variables and constants, comparisons of them, `!`, and a negation, but for an integer's in a debug build, which fails at its type's least value (so `abs` there, which negates only a negative, stays a branch). A choice whose value calls, reads an element or computes anything else is left as it was, and so is an inlined bool function that is a condition itself (`if inside(x, lo, hi) { ... }`), whose returns are branches, as C takes them. Floats are chosen as std chooses them, which Go's builtins do not: Go's `max(1, NaN)` is NaN and its `max(-0.0, 0.0)` 0.0, std's 1 and -0.0. A float's choice is the temporary's assignments, then, which Go compiles to a branch, as it does every float `if`: it makes no select of a float. (Selecting the values' bits instead would make no branch, at the cost of moves between the float and the integer registers on each step of a reduction.)

`test/go/programs/selects.goose` (and its `--debug` twin) checks each choice through both backends at every scalar type, at the ends of each range, with NaNs and signed zeros, into every kind of destination, and next to what stays a branch; `test/go/export/selects/` compares the choices of export fns with Go's, and `run_go_tests.py` reads the code Go makes of each for arm64 and amd64 at -O2 and -O0: a select, and no conditional branch but those of its loop and its guard (`Runner.select_asm`). On an arm64 Neoverse N1 with Go 1.24, `o[i] = max(a[i], b[i])` over 4096 `i64`s takes 4.2 µs on random data as on sorted (`BenchmarkMaxPairsRandom`, `BenchmarkMaxPairsSorted`), where its branches took 12.9 µs and 5.9 µs; `s += clamp(x, 250, 750)` takes 4.7 µs either way, where it took 11.9 µs and 6.2 µs; clamping 4096 random bytes in place 5.2 µs, where it took 10.4 µs; and the max-reduction `m = max(m, x)`, which was a select already, 3.3 µs.

The kernels of issue #26 also kept bounds checks their indices made unnecessary, in gaps of the front end's bounds-check elimination that both backends share: a fact an inlined body states is lost after the body where it returns early, or where it cannot complete; and a loop bounded by its trailing `if c { break; }`, rather than by its condition, keeps every check that bound would remove. `test/go/bce_gaps/` holds a minimal reproducer of each, which `run_go_tests.py` checks with `--bce-test` (`Runner.bce_gaps`), and its README.md writes them up, with their causes in `bce.h`, for upstream.

### 3.10 Shift Counts (issue #27)
A shift computes at its left operand's type and masks its count to that type's width (`goose_spec.md` §6.1, §6.2): with a `u8` `b`, `b << 16` is `b << 0`, so `let v: u32 = b << 16;` stores `b` itself where `(b as u32) << 16` was meant, the slip of assembling an integer from bytes without casting them first. The front end lets every such shift pass. Until it diagnoses them, which [`docs/upstream/shift-diagnostic.md`](docs/upstream/shift-diagnostic.md) proposes to upstream, `--target=go` warns of each shift (`<<`, `>>`, `<<=`, `>>=`) by a constant count outside `0..width-1` of the type it computes at (the left operand's, a constant's `i64`, the target's): `WarnShiftCounts` (`src/codegen_go_shifts.h`), which `src/main.cpp` calls on the checked program before the optimizer folds or inlines anything, so that what it warns of is what the source says, at every -O level. A count is a constant as the checker means one (`Val::ck == CK_INT`): a literal, a named constant, and `-` and the integer operators of constants, but no cast and no local `let`. It walks every specialization's body and every global's initializer, the code that runs (`RunChildren`, a function value's body where it is called), and warns once per shift as the source has it and message: a generic function's `x << 8` at its `u8` specialization, and not at its `u16` one. The warning says what the shift does instead, and for `x << c` how to keep x's bits, the operand cast first to the type its value is widened to at once (the checker fits the shift node to a wider destination or operand, the left operand keeping its type) or else to the narrowest type of its signedness wide enough for the count:
```
prog.goose:9: warning: shift of u8 by 16 is a shift by 0: at u8 the count is masked to 0..7 (§6.2); cast the operand first: `(b as u32) << 16`
```
It is a warning, not an error: the program means what §6.2 defines, and it compiles as the C backend compiles it. Over the programs of upstream's suite and samples, the standard library as they use it, and this repository's other tests, it warns of four lines, all of them the C suite's fixtures of the masking (`codegen_exec.goose`, `constant_widths.goose`, `bce_halving_index.goose`). A left shift whose value is widened at once loses bits whatever its count (`let v: u32 = b << 4;`), which the issue would ideally have warned of too; that rule is broader, and its one hit over the same programs loses nothing (`(s[i] as u16) << 8`, a byte shifted at 16 bits), so the proposal leaves it to upstream to weigh, and the Go backend does not give it. `test/go/warnings/shift_counts.goose` declares every warning it must print with `run_tests.py`'s `// warning:` lines (`Runner.warnings`), and `run_go_tests.py` leaves these warnings out of the two backends' `--check --stacks` reports, which must agree on the rest (`GO_WARNING`).

### 3.11 The Runtime a File Holds (issue #19)
`src/codegen_go_runtime.h` reads the runtime's embedded source (§2) as Go, into its top-level declarations (`GoParseDecls`): each with the names it declares (a method with its receiver's type), its documentation, and the names its text uses, apart from those after a dot, and the packages. `CodeGenGo::Source` reads the program's Go the same way, and so knows which of the runtime's names it uses, and which names it declares itself.

- **What a file holds** (`--go-runtime=embed`, the default). The declarations the program's names reach (`GoRuntimeReach`), and theirs, to the end: a type's methods where it is written and their names are used after a dot (`Error`, which the error interface asks for, always), each in the runtime's order, under the comment of its section, and the imports those name. The roots are the names the program's Go and its `--include` files use, and for a library's host the error an abort panics with (`GsError`) and, where an entry point runs on a block the caller holds, the block API (`NewStackBlock`, `AcquireStackBlock`, `ReleaseStackBlock`, `Close`, `Reset`, `EnsureStacks`). A library of kernels names no block, and holds none of the data stacks, pools or text forms (`test/go/kernels/`). `--go-runtime=full` writes every declaration.
- **The names.** A rename rewrites identifiers of the Go text, not those after a dot nor a method's own name, and, for the unexporting ones, the words of comments: a `//goose:internal` name is unexported in a file that holds the runtime, and `--go-unexported` unexports every exported one (`GsSlice` is `gsSlice`), the first letter only, which changes no length and so no `gofmt` alignment (the runtime refuses to declare two names that would meet). It also unexports the program's own names that Go would export (`Tally_g` is `_Tally_g`), but for the types the entry points' signatures name, and adds the exported alias the `...WithStack` entry points take, `type StackBlock = gsStackBlock`, with `AcquireStackBlock`/`ReleaseStackBlock` where one runs on the block (`--go-no-withstack` leaves those entry points out: `Name` runs on its block through `gsWithStack_Name`, the program's). The program's Go is renamed before it is laid out (`GoFormat`), and so are the `--include` files, which name the runtime as `runtime/go` declares it whatever the mode.
- **`--go-runtime=import`.** The file holds none of the runtime and imports the package as `gsrt`: every runtime name in the program's Go and its `--include` files is `gsrt.`'s (which is why the generated code writes the runtime's structs' literals with their fields' names: `go vet` asks that of another package's). The package is one per process, however many packages import it; a program's configuration, its pool and its workers' cap are its `gsProg`'s, so packages of other sizes share it safely. A host makes blocks for the `...WithStack` entry points from the package's own program (`gsrt.AcquireStackBlock`), of the default sizes.
- **`--go-runtime-file f.go`.** The runtime, and the package's configuration (`gsStackReserve`, `gsStackGap`, `gsFrameReserve`; the package's `gsProg` where the runtime's block API names it; `StackBlock`), go to a file of their own in the package, which its programs share: the program's file holds the program. A compile reads the file where it is there, takes every name it uses for roots too, and writes it again: the closure of what all the package's programs use, the same whichever compiles first. The settings it records on its `// goose-runtime:` line -- the mode, the names, the configuration -- must be the compile's, and its package its; anything else is refused, before a file is written. It has no build constraint, whatever `--go-build` gives a program's file: it is built with whichever of the package's programs are, which may each be constrained otherwise. The program's own names carry its file's name, letters and digits (`-o geom.go`): `x_g` is `x_geom_g`, `ns_x_g2` `ns_x_geom_g2`, and a name of the generated code's own (`gsInitGlobals`, `gsProg`, `gsFile0`) `gsInitGlobals_geom`, so that the package's programs declare names of their own; the entry points keep theirs.

### 3.12 Reproducible Files (issue #21)
A repository that checks generated Go in needs to know what wrote each file, and a check in CI that the file is what its source compiles to. The header records the first, after the line Go's tools know generated code by, `// Code generated by the Goose compiler from prog.goose. DO NOT EDIT.`, which stays as it was (`CodeGenGo::Source`):
```go
// goose-version: 4c34eec (runtime/go 425d07b20272)
// goose-flags: --target=go -O2 --library --go-package stats
```
- **The version** is `goose version`'s, `git describe` of the compiler's source tree as its build found it (`GOOSE_VERSION` for a release), and the runtime's revision a hash of the text of the files of `runtime/go` the build embedded (`GoRuntimeRevision`: FNV-1a, as `goose version` hashes the C runtime, over each file's name and text without carriage returns, in the order of their names), which is the source `--go-runtime=import` imports as well. A runtime file's header (`--go-runtime-file`) records the version too.
- **The options** are the ones the Go depends on, as a command line gives them (`GoHeaderFlags`), each spelled one way, in one order, and only where it is not the default -- but for `--target=go` and the level, which are always there -- whatever spelling the compile had: `-o out.go` for `--target=go`, `-DGS_DEBUG=1` for `--debug`, a `-D` for `--stack-reserve`, `=` or a space, a default given, an export library without `--library`. They are `-O`, `--debug`, `--no-bce`, `--library`, `--go-package`, `--go-build` (quoted for a shell), `--go-runtime`, `--go-runtime-file`, `--go-unexported`, `--go-no-withstack`, the runtime's configuration (`--stack-reserve` where it takes the size, and `-DGS_STACK_RESERVE`, `-DGS_STACK_GAP`, `-DGS_STACK_BUDGET`, `-DGS_MAX_STACKS` and `-DGS_STACK_STATS=1`), `--frame-reserve`, and each `--include` file, named as the file's `//line` directives name it, relative to the file. The other `-D`, which are C's, and `--stdlib`, a place on the machine, change nothing in the Go and are left out. So two compiles that say the same write the same file, and changing `--go-package` changes the header.
- **`--check`.** With `-o out.go`, `goose --check` (and `goose check`) compiles the Go as the compile without it would -- the program checked as that compile checks it, so that one with no `fn main()` that is no library is refused as there -- writes nothing, and compares what it would write with `out.go` and with the `--go-runtime-file`, which it would write again from what the file there holds (`src/codegen_go_check.h`). A file that differs, or is missing, is stale: the compile fails, with exit code 1 and, for each such file, a unified diff with no lines around each change (`diff -U0`'s), its first 24 lines: the fewest lines removed and added, as Myers's algorithm finds them, and past 1000 of them the parts between the lines both files hold once each diffed so, as a patience diff splits a diff. A file that differs in its line breaks alone, `\r\n` where goose writes `\n`, is stale too, and the message says so.
- **The same bytes, wherever they are written.** The Go must depend on nothing but the compile's input -- nothing in it in an order an address or a hash gives -- and name nothing of the machine but what the command line names: the source as given, which the file's abort messages name too, and the `--include` files relative to the file. The standard library is a place on the machine, as a fetched package is, so a file of another package than the program's is named by its place in that package, after the package's name (`stdlib/std.goose`, `FileRef`): an abort there names it so, where the C backend names its whole path, and `run_go_tests.py` compares a C run's messages with the Go's with such a path named so (`go_file_names`). `test/run_go_tests.py`'s `reproducible` section compiles every program of `test/go/programs/` (at -O2 and -O0), every fixture of `test/stdlib/`, the runtime's modes, an `--include` and a shared runtime file in two temporary directories, each with a copy of the standard library, and compares the bytes (`Runner.same_go`).

### 3.13 Bounds Checks (issue #40)
Every index check BCE leaves is `GsIdx(i, n, file, line)` (`IndexLoc`), which Go inlines into its caller: an unsigned compare and a branch to the failure, `panic(gsIdxErr(i, n, file, line))`. `gsIdxErr`, kept out of line (`//go:noinline`), builds the `*GsError`, and the panic statement is the one call Go knows does not return: Go has no way to say so of a function, as C says it of `gs_idxfail` (`GS_NORETURN`), and of a program's calls only a `panic` ends the flow for it. A failure that is a call of a function that panics, as `GsIdx`'s was, Go takes to return to the code after the check, so every value live there -- in a loop, its variables, its slices' pointers and lengths -- is saved to the frame before the call and loaded after it, Go's registers being the caller's to save. With one check in a loop Go saves them in the failure's block; with more, the saves, which must come before every failure that loads them, move out onto the loop's own path, stores of the loop's values every step: in the issue's sorting kernel, the 61 checks of 118 that BCE left made it 40% slower than the same in Go, whose own checks fail through calls Go knows do not return, and `assert(0 <= i && i < a.len)` before each index, which BCE takes as proven and whose abort is a panic once Go inlines `GsAbort`, was the way out. Past a check whose failure ends the flow nothing is live, so nothing is saved, and Go knows the index is in range: the check of Go's own that a Go local's array indexed past `GsIdx` holds (§3.6) goes. The failure is what it was, the same message and location in the same `*GsError`, which the same code recovers (`GsExitOnAbort`, a worker's goroutine, a library's caller). `GsIdx` costs 73 of Go's inlining budget of 80, where it cost 71.

The Go's other checks fail so already. A slice's bounds are checked where it is made (`GenSlice`) and fail through `GsAbort`, as an `assert`, a pop and a capacity do, and a division by zero through `GsDivFail`: each panics, and is small enough that Go inlines it, which makes its panic statement the caller's; `GsSub`, which makes the slice, checks nothing. The debug build's checked arithmetic and conversions (`GsAddI64`, `GsRangeI`, ...) are calls that Go does not inline, whatever their failures are. One limit stays: into a function it takes to be big, of 5000 nodes or more, Go inlines only what costs 20 or less, so that there `GsIdx` is a call, as it was before.

`test/go/export/bounds/` holds kernels whose indices BCE proves nothing of -- heapsort's sift, which reads the children 2i + 1 and 2i + 2, a scan of each node's neighbours in a graph's CSR form, two checks a step of indices that are data, and fields sliced at offsets that are data -- and twins of the first two whose `assert`s prove every index in range first. `run_go_tests.py` reads the code Go makes of each annotated export fn for arm64 and amd64, at -O2 and -O0 (`Runner.spill_asm`): `// asm: no spills` must move no value between a register and a slot of its frame, and `// asm: no index checks` (a Go local's array, indexed by data) must make no check of Go's own; and Go must inline every call of `GsIdx` and `GsSub` (`go build -gcflags=-m`). With `GsIdx`'s failure a call, the sift's code held 40 moves between its registers and its frame on arm64 and 42 on amd64, the scan's 35, and the array kept Go's check. On an arm64 Neoverse N1 with Go 1.24, heapsorting 4096 `i64`s takes 319 µs (`BenchmarkHeapSort`), where it took 389 µs, and 360 µs with the `assert`s, each two compares where `GsIdx` makes one; the same in Go takes 299 µs. The scan of a graph of 1024 nodes of up to 32 neighbours takes 22.3 µs (`BenchmarkRowSums`), where it took 29.9 µs, 35.3 µs with the `assert`s and 29.8 µs in Go, and tallying 4096 bytes into a local array 5.8 µs, as in Go, where it took 6.6 µs (`BenchmarkTally`).

### 3.14 Inlining into Recursive Cycles (issue #42)
The optimizer inlines nothing into a function of a recursive cycle, a `recursive fn` or a member of its cycle (`Optimizer::TryInline`: "Never into a recursive cycle: the inlined body's locals would become the cycle function's own, upsetting the §7.8 stack-assignment rule"), so every call a recursive kernel makes stays a call, a leaf helper's and an `inline fn`'s included: a hash or a comparator at each step of the recursion costs a call, and its body is optimized and bounds-checked apart from what its caller knows. What the rule protects is what each activation holds. A callee in no cycle cannot call into the one it is called from -- that call would have joined it to the cycle (`TypeCheck::JoinCycle`) -- so its locals, inlined, are in scope at no call into the cycle, and the checker's verdict stands; but a nonfixed one would be on a stack of the cycle function's own, and one of more than 4096 bytes would move from a data stack to the native frame (§3.2, `FixedLocal`), which changes the cycle's stacks and the `--stacks` report. A callee that takes no data stack changes neither.

`InlineIntoCycles` (`src/codegen_go_cycles.h`), which `src/main.cpp` runs for `--target=go` right after the optimizer, before BCE, gives each function of a cycle the inlining any other function has, of such callees: the optimizer's own walk over its body again (`Optimizer::OptBlock`), its rule lifted for that function alone, so that a callee is inlined into a recursive fn by the rules of size, use and nesting it would be inlined by anywhere else -- an `inline fn` wherever inlining is on -- and the copy folded as any is. A callee in a cycle never is (`InlineInfo::noinline`, which the optimizer gives every member of one), nor is one whose code, or that of a function it calls, takes a data stack (`GoTakesNoStack`): a value that is not fixed-size or is larger than `NATIVE_VALUE_LIMIT` by a bound of its parts (`GoCycleValueBound`), or a builtin's call that takes one -- a print, a `str`, a `format`, an image's, a spawn's, a wait's or a queue's (`GoBuiltinTakesNoStack`) -- which the pass marks not to inline for its walk. The base cases the optimizer copied into the self-calls (`optimize_basecase.h`) are not copied again, and liveness follows, as at the end of the optimizer's pass: a helper inlined everywhere goes dead. So every activation of a cycle holds the stacks it holds in C, at the same indices, and both backends report the same stacks, which `Runner.stacks` checks over the suite and the fixtures of `--sweep`. The C backend keeps upstream's rule, which [`docs/upstream/recursive-inlining.md`](docs/upstream/recursive-inlining.md) proposes to change. An inlined callee's locals are the cycle function's own, which grow each activation's Go frame by what they hold, as Go's own inlining does.

`test/go/programs/cycle_inlining.goose` runs recursive fns calling each kind of helper through both backends -- an inline fn, an early return, a loop, a local handed by reference, a base case's call, a tail sum the optimizer makes a loop of, a cycle of two functions, a `recursive fn` that does not recurse, a nested one reading its parent's local -- beside helpers that stay calls: one that prints, one building a `str`, one with a 4800-byte local, one calling into another cycle. `Runner.cycles` reads its Go and `test/go/export/string_slices/`'s at -O2: the Go function of each function an `// inlined:` line annotates calls none of the Go functions of the helpers it names, and each one a `// calls:` line names. Go inlines a small leaf into a recursive function itself, a hash's loop included, so what the pass buys is in the callees it does not: on an arm64 Neoverse N1 with Go 1.24, a recursive count of the neighbours in order of a 1024-string table, which compares them with an inline fn through an accessor, takes 22.7 µs where it took 28.0 µs (379 ns where 454 at 16 strings), and a digest of the table whose helpers Go inlined already takes what it took, 23.0 µs; `SortedPairs` of `test/go/export/string_slices/` over a `[]string` of 1024 keys takes 21.6 µs, the same recursion in Go 17.4 µs (`BenchmarkSortedPairs`).

## 4. Using the Go Backend

The command line is in [`docs/command_line.md` §15](docs/command_line.md#15-writing-go---targetgo); in short:

| Command | What it does |
|---|---|
| `goose --target=go -o out.go prog.goose` (or `goose -o out.go prog.goose`) | Writes one Go source file holding the program and the part of the runtime it uses (§2, §3.11), `package main`, which `go build out.go` builds with nothing but Go's standard library and `CGO_ENABLED=0`, laid out as `gofmt` lays it out (§3.7). |
| `goose run --target=go prog.goose [-- args]` | Writes the Go to the program's build directory under `GOOSE_HOME` (as `main.go`), builds it with `go build` and runs it, exiting with its exit code. `goose --target=go prog.goose` does the same. |
| `goose build --target=go prog.goose [-o exe]` | Builds the executable beside the root file, or where `-o` says. |
| `--go-package name` | The file's package: `main` for a program, `goose` for a library by default. |
| `--library` | A package with no `func main` and no `init`, which the first call of an export fn's entry point starts (§3.5): the globals, initialized on a block of its own. Importing it does nothing, and nothing it runs exits the process. A `fn main()` the program has is not run. A file with `export fn`s and no `fn main()` is a library without it. |
| `--frame-reserve size` | The address space each block reserves for its fixed-frame stack (§3.6), from 64 KB: 1 GB by default, 64 MB for a library. Go alone has one. |
| `--include helper.go` | Go source spliced into the file for the `extern fn`s the program calls (§3.5): its package clause and build constraints dropped, its imports merged, its lines kept (`//line helper.go:N` before each run of lines). A C header is refused. |
| `--go-build expr` | Starts the file with the build constraint `//go:build expr` (§3.7), which `go build` honors as it builds the file's package: `--go-build goose_x` makes a file built with `-tags goose_x` only. For the Go `-o` writes; `goose run` and `goose build` refuse it. |
| `--go-runtime embed\|full\|import` | Where the runtime comes from (§3.11): the part of it the program uses, written into the file (the default); all of it; or none, the file importing `github.com/robtandy/goose.go/runtime/go` as `gsrt`. `goose run` and `goose build` refuse `import`. |
| `--go-runtime-file f.go` | Writes the runtime and the package's configuration to `f.go`, beside the `-o` file, which the package's programs share (§3.11): each compile keeps what the others use, the settings must be the same, and each program's own names carry its file's name. For the Go `-o` writes. |
| `--go-unexported` | Unexports the runtime's names and the program's own (§3.11), so that the package exports the export fns' entry points, the types their signatures name, and, for the `...WithStack` ones, `StackBlock` and the two calls that make one. |
| `--go-no-withstack` | Writes no `...WithStack` entry points: an export fn is `Name` alone. |
| `--check` (or `goose check`) with `-o out.go` | Writes nothing: compiles the Go and compares it with `out.go` and the `--go-runtime-file` (§3.12), and exits with 1 and a short diff of each file that is stale or missing. |
| `--debug`, `--stack-reserve`, `-DGS_STACK_RESERVE`, `-DGS_STACK_GAP` | As for C: the checked arithmetic and casts of §3.1, and the size of each data stack's reservation and guard gap (§2.1), which the compiler reads as integer constants and writes into the file (`gsStackReserve`, `gsStackGap`). |

An `export fn name` is two Go entry points (§3.5), named after its symbol with each word capitalized: `Name(args...)`, on a block from the runtime's pool, and `NameWithStack(gs, args...)`, on a `*GsStackBlock` the caller holds; and where a `const u8[:]` parameter makes them generic, `NameString(args...)` and `NameBytes(args...)`, which take it as a `string` and as a `[]byte`. A Go program imports the library's package and calls them:

```go
n := stats.CountWords("the quick brown fox")   // export fn count_words(text: const u8[:]) -> i64
gs := stats.AcquireStackBlock(0)                // or stats.NewStackBlock, and gs.Close()
defer stats.ReleaseStackBlock(gs)
m := stats.MedianWithStack(gs, []int64{9, 1, 7}) // export fn median(xs: i64[:]) -> i64
```

The README has the whole example, and one of `--include`.

## 5. Testing: `test/run_go_tests.py`

`python3 test/run_go_tests.py` checks the Go backend against the C backend. Every program it runs is compiled by both, at `-O2` and, but for the generated overflow and `--fuzz` programs, at `-O0` too, where nothing is inlined and every call stays a call. The Go must pass `go vet` with `CGO_ENABLED=0` (the `unsafeptr` analyzer included) and `gofmt -l`, which must find nothing to change in any file the suite writes (§3.7), build, and run exactly as the C does -- stdout, stderr and exit code -- also when built with `-gcflags=all=-d=checkptr` (at `-O2`), which checks every `unsafe.Pointer` conversion and the arithmetic on one at run time (what `go test -race` turns on, without cgo). Both backends must print the same `--stacks` report, which their shared accounting gives (`src/codegen_stacks.h`), and the runs must print what the expected files hold. Its sections:

|---|---|
