# `goose.go` Architecture & Design

## 1. Compiler Pipeline Integration

The Goose compiler (`src/main.cpp`) executes six passes over the AST (`src/ast.h`):
1. **Parse** (`src/lexer.h`, `src/parser.h`) -> `Ast`
2. **Resolve** (`src/resolve.h`) -> type aliases & namespaces resolved
3. **Typecheck & Monomorphize** (`src/typecheck*.h`) -> clones one `FnSpec` per live specialization, enforces all reference root, provenance, writability, shrinking, and lifetime rules (§3–§11 of `docs/goose_spec.md`)
4. **Optimize** (`src/optimize*.h`) -> function inlining, constant folding, base-case inlining, tail-recursion elimination, loop strip-mining
5. **Bounds-Check Elimination (BCE)** (`src/bce.h`) -> marks `Index::nobc = true` and `SliceExpr::nobc = true` wherever bounds are statically proven safe, plus loop hoisting (`hoistrefs`, `hoistfields`)
6. **Codegen**:
   - Existing C backend: `src/codegen*.h` (`CodeGen`)
   - **New Go backend**: `src/codegen_go*.h` (`CodeGenGo`), selected via `--target=go` (or automatically when `-o <file>.go` ends in `.go`).

Because `CodeGenGo` runs **after** `TypeCheck`, `Optimizer`, `BCE`, and `BoundStacks` (`src/codegen_stacks.h`), it receives:
- Fully monomorphized `FnSpec`s with exact static stack counts (`fn->numstacks`, `BoundStacks`)
- Already-inlined hot functions (bypassing Go `cmd/compile`'s 80-node inlining budget)
- Proven `nobc` flags on array/slice indexing (allowing `CodeGenGo` to emit raw `unsafe.Add` loads/stores without Go slice bounds checks).

## 2. Pure-Go Data Stack Runtime (`runtime/go/`)

### 2.1 Virtual-Memory Data Stacks (`syscall.Mmap`)
- Each Data Stack reserves `GS_STACK_RESERVE` bytes (default 2 GB, configurable) + `GS_STACK_GAP` (1 MB) of anonymous virtual address space via:
  ```go
  syscall.Mmap(-1, 0, reserve+gap, syscall.PROT_READ|syscall.PROT_WRITE, syscall.MAP_ANON|syscall.MAP_PRIVATE)
  ```
- The trailing `GS_STACK_GAP` is marked `syscall.Mprotect(gapSlice, syscall.PROT_NONE)` so runaway stack growth triggers an immediate OS fault at the guard page rather than corrupting memory.
- If the OS refuses a 2 GB reservation (e.g., strict `ulimit -v` or `vm.overcommit_memory=2`), `gs_reserve_region` halves the reservation size down to a minimum of 1 MB, matching C Goose (`src/runtime/runtime_impl.h`).
- Physical RAM pages are demand-paged by the OS kernel only as the stack top (`Top`) advances.

### 2.2 Goroutine-Safe `GsStackBlock` & `sync.Pool`
Unlike C threads (`__thread`), Go goroutines multiplex across OS threads and a process may have tens of thousands of idle goroutines.
- Instead of OS thread-local storage, `goose.go` encapsulates a thread/worker program's Data Stacks in a `GsStackBlock`:
  ```go
  type GsStackBlock struct {
      Stks []unsafe.Pointer // current stack tops, indexed by gs_sp + k
      Base []unsafe.Pointer // base addresses of each reserved mmap stack
      Cap  []int64          // reserved byte capacity of each stack
  }
  ```
- Every generated Go function that uses Data Stacks (or calls one that does) takes `(gs *GsStackBlock, gs_sp int64, ...)` as its leading parameters—mirroring C Goose's `int64_t gs_sp` hidden parameter (`docs/implementation.md` §6.2).
- A global `sync.Pool` of `*GsStackBlock` instances (`AcquireStackBlock(numStacks int)` / `ReleaseStackBlock(gs *GsStackBlock)`) allows exported Go entry points (`export fn`) to check out a `GsStackBlock` in ~15 ns, run the entire CPU-bound Goose computation with 0 GC allocations, rewind stack tops to `Base`, and return the `GsStackBlock` to the pool.
- Callers can also manage a `*GsStackBlock` explicitly (`NewStackBlock` / `Reset` / `Close`) to keep parsed DOMs or zero-copy structures alive across multiple calls on the Data Stack before rewinding in $O(1)$.
- A block also carries the program instance it runs, in a program with workers (`Gl`, §2.3), and which worker runs on it.

### 2.3 Workers, Queues and Program Instances (`goose_spec.md` §11.2)
`src/codegen_go_threads.h` compiles Goose's concurrency as the C backend does (`codegen_builtins.h`, `runtime_threads.h`, `docs/implementation.md` §6.3, §6.8); the runtime it calls (`go_runtime_threads` in `src/codegen_go_runtime.h`, and `runtime/go/goose_threads.go`) is written into a file that uses it.
- **A worker** is a goroutine running its thread program on a `GsStackBlock` of its own, which it reserves as it starts (`GsThreadSpawn`, `gsThreadMain`): the data stacks its program counts, then the dedicated ones its arguments and globals land on, its fixed-frame stack, its program instance, and a private copy of its spawn packet, which the spawn takes, all outside the Go heap. The goroutine releases all of them (`Close`) before it publishes its end, which is what `thread_wait` waits for; ids increase from 0 and are never reused, and a wait on an unissued id or on the waiting worker itself aborts (`GS_E_THREADID`, `GS_E_THREADSELF`).
- **`thread_spawn`** packs the arguments contiguously on a scratch stack, then each global the worker's program reaches as `[int64 size][image]`, as C's does: a fixed-size value's bytes, a bytes value's image, a resizable's count, a frame object's fixed fields (packed) and its elements, a pool's freelist after its elements. The worker's thunk (`gsTmain_<worker>`) unpacks them onto its block's dedicated stacks and into its instance and runs the body with its stacks from 0; a fixed-size argument of more than 4096 bytes stays in the packet, which the worker owns, as C passes one. `--stacks` reports each worker's stacks and the thread cap as C's does.
- **Aborts.** Every abort panics with a `*GsError`; each thread program's goroutine recovers it. A contained worker (`thread_spawn_contained`) keeps the message of one with a location for the first `thread_wait(id, msg)` that asks, and its waits answer `false`; anything else -- an abort in main or in a worker that is not contained, the runtime's own failures, a fault in a guard gap (`debug.SetPanicOnFault` is set per goroutine) -- ends the process, with one report, from whichever goroutine (`gsEnd`), as `exit(code)` does. A library never exits the process, which is its host's (`gsLibrary`, §3.5): there `exit(code)` panics with a `*GsError` too, and what would end the process stays the panic of its `*GsError`, which an export's caller can recover. On a worker's goroutine, which the runtime started, no host can, and the process ends as it does for any goroutine's unrecovered panic.
- **Program instances.** In a program that spawns workers, every global that is not read-only static data (`CStaticInit`, which every instance shares as it is) is a member of `gsGlobals`, one instance per thread program: main's is the static `gsGlobalsMain`, a worker's the copy its spawn took. A function that names one reads the instance from its block once, `gs_gl := (*gsGlobals)(gs.Gl)`, and so takes the block; a global's dedicated stack is the block's stack its instance names (`gs_gl.gsGStk_<name>`), and the channels of `return ... from` are members too. A program without workers keeps its globals in package variables, at no cost.
- **Queues** are a `GsQueue` per element type, a FIFO of value images (the same images a spawn packs) under a mutex: `qput` copies before it locks and never waits, refusing a put at the queue's limit (`qlimit`, `GS_E_QBOUND` below one); each waiting receiver waits on a channel of its own, so a timed `qget<T>(ms)` waits for a monotonic deadline; a miss yields `T`'s zero value; a value of no bytes is a message of none.
- **`hardware_threads()`** is `runtime.GOMAXPROCS(0)`, capped at the workers `GS_STACK_BUDGET` holds beside the main program, at least one (`gsRtStart`, as `gs_rt_start` computes it).
- What differs: recursion deeper than a goroutine's stack holds is a fatal error of the Go runtime at 1 GB, where C reports its native stack's overflow as an abort, in a worker as in main (`test/threads/thread_stack_overflow.goose`).

## 3. Value Representations in `--target=go` (`docs/implementation.md` §6.1)

### 3.1 Scalars & Integer Semantics
- `i8`, `i16`, `i32`, `i64` -> `int8`, `int16`, `int32`, `int64`
- `u8`, `u16`, `u32`, `u64` -> `uint8`, `uint16`, `uint32`, `uint64`
- `f32`, `f64` -> `float32`, `float64`
- `bool` -> `bool` (1 byte, 0 or 1 in binary layouts)
- In release mode (`GS_DEBUG == 0`), arithmetic and casts emit native Go operators (`+`, `-`, `*`, casts), with `gs_f2iwrap` for float-to-int wrapping and zero-checked division/Euclidean modulo (`gs_div_*`, `gs_mod_*`).
- In debug mode (`--debug`), arithmetic and narrowing `as` casts call checked helpers (`gs_add_i32`, `gs_range_*`, etc.) that report the `.goose` file and line on overflow.

### 3.2 Fixed-Size Types (`Fixed` Class)
Goose specifies exact byte layouts (`FixedSize`, `LayoutFields` in `src/codegen_types.h`) with `#pragma pack(1)` semantics. `src/codegen_go_types.h` ports them and keeps every fixed-size value in its C layout, byte for byte, its references and slices included:
1. **Naturally Aligned Structs holding no address** (where every field offset in `LayoutFields` already matches Go's natural alignment and total size matches `FixedSize`, such as `struct YyVal { tag: u64, uni: u64 }`):
   - Emitted as a native Go `struct` so field reads/writes are direct `s.tag_g` / `s.uni_g`; `pad` and `pad n` become blank `_ [n]byte` fields, which Go's `==` ignores as Goose's does.
2. **Every other Fixed Struct & Fixed-Mode ADT** (unaligned offsets, no tail padding, or a reference or slice among the fields):
   - Emitted as `type Name_g [FixedSize]byte`, each field read and written in place at its exact byte offset from `LayoutFields`: `*(*uint32)(unsafe.Add(unsafe.Pointer(&s), off))`.
   - On `arm64` and `amd64`, Go's SSA compiler lowers that to a single unaligned load/store instruction (`LDR`/`STR` or `MOV`).
   - A payload-less ADT is its tag, a named `uint8`/`uint16`; any other fixed-mode ADT the bytes of its tag (`TagStore`) and its largest payload, the payloads overlapping behind the tag as C's union. A static-capacity limited array `T[..k]` is its length (`LenStore`) and its `k` slots, as a native struct where Go aligns the slots and they hold no address, and as bytes otherwise; a fixed array `T[k]` is a Go array.
3. **References and slices.** A plain or optional reference is a typed Go pointer (`*T`, `nil` for null) and a slice a `GsSlice { Data unsafe.Pointer, Len int64 }`; a reference to a value whose Go type itself holds Go pointers (a slice, an array of references) is its `unsafe.Pointer` address. Every address a program holds points outside the Go heap and never moves: into a data stack, into the fixed-frame stack (§3.6), into a global or into a literal's static data. So a value's bytes can hold one where the collector does not look, which needs no write barrier either. A value of a Go type holding Go pointers at an address that may be unaligned (a slice at byte 1 of a struct's bytes, a reference packed on a data stack) is read and written through a copy of its bytes, `gsLd_<T>`/`gsSt_<T>` (`*(*[16]byte)(unsafe.Pointer(&v)) = *(*[16]byte)(p)`), which has alignment 1: `checkptr` accepts it where a typed access would be a misaligned pointer conversion. A self-relative reference is the signed offset C stores, at its width, from the offset C gives its field.
4. **Equality** (`==`, §4.5) is Go's own `==` wherever that is the structural one (native structs of scalars, the bytes of a value whose bytes are its equality, references and slices, arrays of them, tags), and a generated `gsEq_<T>` elsewhere, which compares a limited array's live elements and an ADT's live payload only, and floats by value.
5. **Large values.** A fixed-size value of more than 4096 bytes is one the C backend holds on a data stack wherever it is a local or a temporary (`FixedLocal`). Those stacks are counted in the `--stacks` report both backends share, so this version supports such values where it takes the stacks C does: in globals (built in place, counting the one stack C's initializer takes, or none where C makes the global static data), in a recursive cycle's locals (which take none, in the function's frame), and on a data stack where C takes one too (`CodeGenGo::FixedLocal`): a named local, a literal's or a `default()`'s temporary, a queue's value, and a `thread_fn`'s argument, which stays in its spawn packet. A parameter or result of one, and its other temporaries, are not supported yet.

### 3.3 Variable-Size Byte Images (`Bytes` Class)
- Represented as `unsafe.Pointer` pointing to the start of the self-describing byte image on a Data Stack.
- Fields after a variable-size field are reached via generated `gs_size_<T>(p unsafe.Pointer) int64` walkers and `unsafe.Add(p, offset)`, identical to C Goose (`FieldPtr`, `SizeX`).
- **An ADT adapted from another type.** Where the checker adapts the result of a call -- a function's, a case function's, a builtin's or a function value's -- or of an inlined body to an ADT it does not arrive as (a variant to its ADT, or an ADT to its other mode, `goose_spec.md` §3.5), the value is built as the type it arrives as and converted, as C builds it (`CodeGenGo::AdtFrom`, `GenAdtAdapted`, after `CodeGen`'s): a variant becoming the variable-mode ADT is built behind the ADT's tag; a fixed-mode ADT becoming the variable-mode one is built in a local and written out as the image of the variant it holds; a variable-mode value becoming the fixed-mode ADT, a reference's pointee included, is built on a temporary stack, taken before the call as C takes it, and read from there. A result a return forwards is adapted at the function's destination for it the same way (`GenForward`). Each call is made once, and both backends take the same stacks. A fixed-size value holding relative references adapted so is not supported yet.

### 3.4 Resizable Data-Stack Values (`Resizable` Class) & Slices
- **Slices (`T[:]`)**:
  ```go
  type GsSlice struct {
      Data unsafe.Pointer
      Len  int64
  }
  ```
  (with zero-copy conversion helpers to/from Go `[]T`, `[]byte`, and `string` via `unsafe.Slice` and `unsafe.String`).
- **Resizable Headers (`GsRhdr`)**:
  ```go
  type GsRhdr struct {
      Base unsafe.Pointer
      Len  int64
  }
  ```
  Elements live contiguously on `gs.Stks[gs_sp + k]`. Pushing an element writes `*(*T)(gs.Stks[stk]) = elem` and advances `gs.Stks[stk] = unsafe.Add(gs.Stks[stk], sizeof_T)` + `hdr.Len++`.
- **Fat References (`GsRref`) & Pool References (`GsPref`)**:
  ```go
  type GsRref struct {
      Hdr *GsRhdr
      Stk int64
  }
  type GsPref struct {
      Hdr     *GsRhdr
      Stk     int64
      FreeHdr *GsRhdr
      FreeStk int64
  }
  ```

### 3.5 `export fn` and `extern fn` in Go Mode
`src/codegen_go_export.h` holds the foreign boundary.

- **`export fn`.** Every `export fn foo(a: u8[:], x: i64) -> i64` gets two exported Go entry points, named by its C symbol's words capitalized (`parse_json` is `ParseJson`, `export "sym" fn` renames it):
  1. `func FooWithStack(gs *GsStackBlock, a []byte, x int64) int64` runs it on the data stacks of a block the caller holds (from `NewStackBlock`, or `AcquireStackBlock`), which it gives back as it found them: a caller may keep one block across calls.
  2. `func Foo(a []byte, x int64) int64` takes a block from the runtime's pool (`AcquireStackBlock(n)`, `n` the export's own stack count), calls `FooWithStack`, and rewinds and returns the block (`ReleaseStackBlock`) before returning. Once the pool holds a block, a call allocates nothing on Go's heap (`testing.AllocsPerRun == 0`, `test/go/export/`). An export whose code needs no block calls the function directly.

  The parameters are Go's own values, viewed in place with no copy: `u8[:]` is a `[]byte`; `const u8[:]` either a `string` or a `[]byte` (a type parameter `T ~string | ~[]byte`, `GsBytes`); any other `T[:]` a `[]T`; `T&` a `*T`; a scalar or a fixed-size value its Go type. What a slice or a reference points at must be flat, as in C (`goose_spec.md` §7.10): a Go struct holding a slice cannot cross yet, and [`docs/design/go_views.md`](docs/design/go_views.md) designs read-only views of one (issue #30). A `const u8[:]` result is a `[]byte` viewing what the slice does (the arguments, a global, static data): no export's result can view the block's stacks, which Goose's lifetimes keep a result from pointing into, so `Foo` always gives the block back. What the entry points are handed may end up where only the data stacks see it, so they keep it off Go's moving goroutine stacks (`gsEscape`: a caller's buffer is on the heap, or static), and alive until the call returns (`runtime.KeepAlive`): Go keeps a value alive only up to its last use, which may be the call itself, and the collector does not see what a data stack, the fixed-frame stack or the bytes of a value hold (issue #30, `test/go/export/keepalive/`). An abort panics with a `*GsError` in the caller's goroutine. `--library` (or `export fn`s and no `fn main()`) makes the file a package with no `func main`, `package goose` unless `--go-package` says otherwise, which starts at the first call of an entry point.
- **A library's start** (issue #18). The package has no `init`: importing it maps no memory, leaves every goroutine's fault handling alone and runs no initializer, so that a host pays nothing for a library it imports for a path it may never take. The first call of either entry point of any export starts it, once, on the caller's goroutine (`gsLibStart`, a `sync.Once` behind an atomic flag): the runtime (`gsRtStart`), the package's block, and the globals' initializers on it. After that a call pays an atomic load for the start, which costs nothing measurable where Go still inlines the entry point into its caller, as it does the smallest (`Twice` of `test/go/export/exports/`); a larger one that Go inlined before no longer fits Go's budget, the start's call to its slow path counting against it, and costs its caller a call. A start that panics -- an initializer's abort, or a fault in a guard gap, which is the overflow's `*GsError` (`gsAbortOf`) -- leaves the globals unusable: that call and every later one panic with what it did. (An `--include` function that an initializer calls cannot call its package's entry points: such a call would wait for the start it is part of.) Nothing a library runs exits the process, which is its host's: `exit(code)` panics with a `*GsError` naming the status, as an abort does (`gsLibrary`, §2.3). A call that runs on a block (`FooWithStack`, and so `Foo`) turns panic on fault on for itself only, `defer debug.SetPanicOnFault(debug.SetPanicOnFault(true))`, so that a stack that grows into its guard gap panics in the caller's goroutine, which can recover it, where it would otherwise kill the process, and gives the caller's setting back as it returns or panics; an export whose code takes no block cannot fault so and leaves the setting alone. That costs a call about 5 ns on an arm64 Neoverse N1 with Go 1.24 (`BenchmarkFaultScope` against `BenchmarkNoScope` in `test/go/export/lazy/`: 7.3 ns and 2.1 ns), the deferred call being made through a closure Go builds for its argument: `ChecksumWithStack(gs, "ab")` of `test/go/export/exports/` takes 23.5 ns where it took 18.1, `Checksum("ab")` 58 ns where it took 51, and `JsonSumWithStack` 751 ns as it did. A library's blocks reserve 64 MB of fixed-frame stack each where a program's reserve 1 GB (§3.6).
- **Concurrency.** Each call of `Foo` runs on a block of its own, so goroutines may call exports at once; making blocks is goroutine-safe, and a pooled block the collector drops is closed. In a program without workers, Goose's globals are the package's, shared by every call, as are `return ... from`'s channels: an export that writes a global is not safe to call from two goroutines at once. An export whose calls reach a global that lives on a data stack of its own (growing it, or handing on a reference to it) is refused at compile time, since that stack is in the program's block, not the caller's.
- **Concurrency with workers.** In a program with workers (§2.3), a call runs on a program instance of its block's own, so no two goroutines share a global, as no two Goose threads do. `FooWithStack(gs, ...)` gives a block that has none a copy of the package's instance (`gsEnter`: main's, which the library's start or `fn main()` leaves), the values on data stacks onto the block's own dedicated stacks at the main program's indices; the block keeps it, and what its calls write, until `Reset` or `Close`. `Foo(...)` copies the globals its calls reach into the pooled block for the call (`gsEnter_<fn>`), so it always starts from the package's, and hands back a result viewing them as a copy on Go's heap (`GsKeep`), its block going back to the pool. Such an export may grow a global's stack, which is its block's; one whose calls reach a global holding a reference into a data stack is refused. The queues are the process's, one per element type, shared by every instance (§11.2).
- **`extern fn`.** A call calls the Go function its C symbol names, directly. The C runtime's functions that std, math and os bind are the Go runtime's (`gs_find_any` is `GsFindAny`, `gs_os_read_file` `GsOsReadFile`; the OS layer behind `stdlib/os.goose` is written into a file that calls it), and the C library's that Go's `math` has are those (`floor`, `sinf`, ...; `mul_add` is `math.FMA`, rounded once, as C's is on arm64). Any other symbol is a Go function of the generated file's package, from an `--include helper.go` (or a file beside the generated one): scalars are Go's types, a fixed-size value its generated type (`Pt_g`), a plain reference a pointer to it, a slice a `GsSlice` (`GsSliceToBytes`, `GsSliceToString` view it), and a `u8[>..]&` builder a `GsRref`, after the block, which such a function is handed first to append with (`GsBldAppend(gs, b, data)`, `GsBldAppendString`). It may not shrink the builder or keep what it is handed past the call.
- **`--include helper.go`** is Go source spliced into the file: its package clause and build constraints are dropped, its imports join the file's own, and the rest follows the program, each run of its lines between blank ones under a `//line helper.go:N` directive naming the run's line (`GoIncludeLines`), so Go's errors in it and its panics' frames name its own lines whatever `gofmt` makes of the blank lines between the runs. A run that opens with a declaration's doc comment takes its directive at the comment's end, after an empty comment line, where `gofmt` keeps a directive in a doc comment.

### 3.6 The Fixed-Frame Stack (`gs.Frame`)
A Goose local whose address the program never takes is a Go local, which Go keeps in registers. One whose address it does take (`&x`, `x[..]`, a by-reference argument, a field access of a value held as bytes) cannot be: Go may move its goroutine's stack while the bytes of a value, a data stack or a frame hold its address, and the collector scans none of those. Each `GsStackBlock` therefore has one more `mmap` region, the fixed-frame stack: a function holding such locals (or parameters) takes its frame there as it starts, `gs_fr := gs.Frame; gs.Frame = unsafe.Add(gs_fr, gs_fo<n>)`, each local a pointer to its slot, and gives the frame back at every return and where its body's end is reached. Fixed-size locals never grow, so the frames obey a strict call discipline, recursion included, and a local declared in a loop has the same slot every iteration, as C's does. Each slot is 8-aligned and at least a byte, so that two variables never share an address, a zero-length array's or a payload-less variant's included. `FinishBody` (`src/codegen_go_emit.h`) finds those locals once a body is generated and rewrites their declarations and uses; whether a function then takes the block is settled once every body is (`ResolveGsArgs`). The region's reservation is address space only: 1 GB in a program, the most Go grows a goroutine's stack to, and 64 MB in a library, whose calls' frames C would run on its host's native stack, 8 MB by default on Linux (`--frame-reserve` sets either, as `gsFrameReserve`). A frame that does not fit is reported as C reports its native stack's overflow.

Indexing a fixed array takes no address of it (issue #23). An element of a fixed array that is a Go local's own -- a local's, a parameter's, a temporary's, or a part of one that no pointer leads to, such as a field of a native struct or an element of an outer array (`GoLoc::golocal`) -- is Go's own index expression, `r_g[i]`, its index checked by `GsIdx` or proven in range by BCE (Go's own check then always passes, and Go removes it where it can prove it too), and its bytes are sliced where a wide load or store takes them (§3.8). So a `u8[8]` that a function fills and reads a byte at a time, in a loop or not, stays a Go array in registers or on Go's stack, and the function needs no frame, nor the block for one; only a use of its address -- a reference to it or to an element, a slice of it, a by-reference argument, printing it -- still moves it into the frame. An assignment to an element pins nothing: the place is the same wherever it is evaluated, and only its bounds check, where it has one, runs before the right side does (`PinLoc`).

Nor does handing a local to an inlined function by reference (issue #24). A function inlined into its caller -- an `inline fn`, or any small helper the optimizer inlines -- binds each `T&` parameter to its argument at the start of its body, where a call would pass the address. A parameter bound so to a place of a Go local's own (a local, a parameter, a field or an element of one: `GoLoc::golocal`) is that place, and no Go variable (`BindRefPlace`): the body reads and writes `tag_g` where it read and wrote `(*tag_g_2)` through `var tag_g_2 *uint64 = &tag_g`, which made `tag_g` a slot of the frame. Its reference value is the place's address as `RefOfLoc` spells it, `&tag_g`, and every dereference of a reference value looks that text up (`RefPlace`: `DerefLoc`, `CoerceVal`, `AtRef`), so that it is the place again wherever the body dereferences it, a parameter handed on to another inlined body included. The place's bounds check, where it has one, runs where the argument is bound, as the binding's would (`_ = a_g[GsIdx(t5, 4, ...)]`), whether the body reads the reference or not; its index is a snapshot, so the place stays the element it was bound to whatever the variable that indexed it holds later. Only a use of the reference as a value spells the address -- handing it to a call that stays a call, storing it in a variable or a field, returning it, comparing its identity, slicing the place -- and those locals alone move into the frame, as every local handed by reference did. A parameter a nested function reaches (which takes the address of the parameter itself), one a `var` may rebind, an optional one, and one bound to anything but such a place (a global, a pointee, a value on a data stack, a construct choosing one of several) are the Go pointer they were. The parser-shaped loop of `test/go/export/inline_refs/`, six scalars of state that one inlined helper takes by reference a byte at a time, scans 4 KB of JSON-like text in 15.1 µs on an arm64 Neoverse N1 with Go 1.24 (`BenchmarkScan`, 283 MB/s), where it took 19.8 µs with the six in the frame (217 MB/s); the same loop written in Go takes 15.7 µs (`BenchmarkScanGo`), and the issue's `inline fn bump(x: i64&) { x += 1; }` in a loop of 1000 takes 0.51 µs where it took 2.28 (`BenchmarkBumps`). A function whose frame held nothing else no longer takes the block for one (`ResolveGsArgs`).

### 3.7 The Layout: `gofmt`'s
A generated file is laid out as `gofmt` lays it out, so that `gofmt -l` finds nothing to change in it (`src/codegen_go_format.h`). The runtime's text is `gofmt`'s already, and the imports are one group in `gofmt`'s order. The program's Go is written a statement or a declaration to a line with `gofmt`'s indentation, and `GoFormat` lays the finished text out as `go/printer` prints the same Go: it parses each line's expressions as `go/parser` does and spaces each binary operator as `go/printer` does, from the depth and the precedences around it (`a + b` at a statement's top, `f(a+b, c)`, `x[i+1]`, `a*b + c`), which is not known where an expression is generated, inside out; leaves out the parentheses `gofmt` does not print (the outer of two pairs, those around a control clause's expression); aligns the fields of a struct, the specs of a `const` or `var` group and the comments ending consecutive lines in `text/tabwriter`'s columns; and keeps one blank line where `gofmt` keeps one, adding the one it puts before a comment or a declaration of another kind at the package level. `--go-build 'expr'` starts the file with `//go:build expr`, the expression checked and written as `gofmt` writes it (`GoBuildConstraint`), and a blank line. An export fn's Go documentation is its Goose documentation's text as one paragraph, which `go/doc/comment` leaves as it is.

### 3.8 Wide Loads and Stores (issue #23)
The usual way to read a little-endian word from bytes is to OR them together, each shifted to its place, and to write one, to take it apart a byte at a time:
```goose
let c = s[i..i + 8];
let w = c[0] | (c[1] as u64) << 8 | (c[2] as u64) << 16 | (c[3] as u64) << 24 |
    (c[4] as u64) << 32 | (c[5] as u64) << 40 | (c[6] as u64) << 48 | (c[7] as u64) << 56;
for k in 8 { o[j + k] = (w >> (8 * k)) as! u8; }
```
A C compiler makes each of these one load or one store. Go's makes one only where every byte's address is a constant away from one base it knows is no nil pointer -- a byte read through the slice's own pointer, at offset 0, keeps the rest apart with its nil check -- and never of a loop, so `src/codegen_go_wide.h` recognizes them and writes each as `encoding/binary` would: `binary.LittleEndian.Uint64((*[8]byte)(p)[:])`, `binary.BigEndian.PutUint32((*[4]byte)(p)[:], v)`, or for a Go local's own array (§3.6) `binary.LittleEndian.Uint64(r_g[0:8])`. Go compiles that to one load or store, with a byte swap for the other order, on arm64, amd64 and every other target with unaligned accesses, and to the bytes elsewhere: the value is the same on every target, its byte order included, and the conversion to an array pointer has no check but for nil, where `unsafe.Slice` would check that the address cannot overflow on every load. Recognized are:
- **Loads**: an OR of 2, 4 or 8 bytes, each `a[e + c]` widened (`as T`, or implicitly) and shifted left by a constant, at consecutive constants `c` of one array or slice `a` and one index `e` (or at constant indices), each byte shifted to its place in a little-endian or a big-endian order, the leaves in any order or grouping, at any integer type of enough bits; an OR at a wider type is the load zero-extended (`c[0] | (c[1] as u64) << 8` is a 2-byte load into a `u64`).
- **Stores**: `for k in n { o[e + k] = (v >> (8 * k)) as! u8; }` (or `0..n`, `k << 3`, and the big-endian `8 * (n - 1 - k)`, `56 - 8 * k`), and a run of n statements `o[e + c] = (v >> s) as! u8` storing every byte once, in either order, n being 2, 4 or 8, the low n bytes of a `v` of at least as many.

Only where nothing could tell the difference: every byte's bounds check is gone already (`Index::nobc`, or a constant index within a fixed array), so that no check in between could abort; the array is one path that nothing between could move (no call anywhere); the index's arithmetic is 64-bit, where a constant added to an index in range cannot wrap to another one in range (`255 + 1` as a `u8` is 0); every type a byte's value passes through holds it whole, as a zero extension does (an unsigned one of enough bits, or the result's own); and a store's value and index are scalar variables and constants, which the bytes it writes cannot change, its conversion to `u8` one that truncates (`as!`, `as` in a release build, or a value masked to 255 first). The leftmost byte's index is evaluated, as the program would evaluate it first. Anything else is left as it is written, a byte at a time.

The recommended pattern, then, is to prove the span once and to write the bytes out: a slice of the span, `let c = s[i..i + 8];`, and constant indices into it; or a guard BCE can use whatever `i` is, `if i < 0 || i > s.len - 8 { ... }`, and `s[i + c]` (`i + 8 > s.len` is no guard of an arbitrary `i`, since `i + 8` can wrap); or a loop whose condition bounds the index, `while i <= s.len - 8 { ...; i += 8; }`. No `extern fn` doing `binary.LittleEndian.Uint64` is needed, and the C backend gets its one load from the C compiler the same way. `test/go/programs/wide_bytes.goose` (and its `--debug` twin) reads and writes every width in both orders at every offset of slices of every length up to 20, the last bytes included, in each recognized form and in forms left alone, against values worked out a byte at a time; `test/go/export/wide/` compares the loads and stores of export fns with `encoding/binary`'s, and `run_go_tests.py` reads the code Go makes of each for arm64 and amd64: one load or one store (`Runner.wide_asm`). On an arm64 Neoverse N1 with Go 1.24, summing the little-endian words of 4 KB takes 0.43 µs written so (`BenchmarkSumLe64`, 9.6 GB/s), 1.6 µs with `+` in the place of `|`, which is no OR of bytes and stays a byte at a time, and 0.63 µs in Go with `binary.LittleEndian.Uint64(s[j:])`, whose bounds check stays in the loop.

### 3.9 Selects (issue #26)
std's `max` is `if a < b { return b; } return a;`, and inlined, a body is a labeled `switch { default: }` whose every exit assigns the destination. Go makes a conditional select of an `if` (`CSEL` on arm64, `CMOV` on amd64) only where its sides do no more than give an integer local of two bytes or more one of two values: a choice stored into an element is a store on each side, and so a branch; `clamp`'s three exits and `sign`'s are branches; and amd64 has no conditional move of a byte, so a byte's `max` is a branch there. `src/codegen_go_select.h` writes a body that only chooses among values it computes nothing for -- std's `min`, `max`, `clamp`, `abs` and `sign`, inlined or not (a function's own body, at -O0), a function of the program's own written so, as guards, an else-if chain or an if's two returns, and an if choosing between values -- in the shapes Go makes selects of:
- **Go's builtin `min` or `max`** (Go 1.21) of a choice of x or y by a comparison of the two integers, `m = max(a, b)`, whichever of the four orders compares them and whichever way round it picks: equal integers are the same value, so how the comparison breaks a tie does not matter. The destination is assigned once, as a store of one value.
- **Otherwise, a temporary** given the value no condition picks, then each other value under its condition, the first condition last, so that it wins as it did by being tested first; the destination is assigned once, after: `t := x; if hi < x { t = hi }; if x < lo { t = lo }; o[k] = t` is two selects and a store.
- **A byte's choice at four bytes**: `uint8(max(uint32(a), uint32(b)))`, or a `uint32` temporary, where amd64 has a conditional move; extending a byte keeps its order.

Only where nothing could tell the difference: every condition and value is computed whichever value is chosen, so each must be one that nothing in runs a statement or can fail -- scalar variables and constants, comparisons of them, `!`, and a negation, but for an integer's in a debug build, which fails at its type's least value (so `abs` there, which negates only a negative, stays a branch). A choice whose value calls, reads an element or computes anything else is left as it was, and so is an inlined bool function that is a condition itself (`if inside(x, lo, hi) { ... }`), whose returns are branches, as C takes them. Floats are chosen as std chooses them, which Go's builtins do not: Go's `max(1, NaN)` is NaN and its `max(-0.0, 0.0)` 0.0, std's 1 and -0.0. A float's choice is the temporary's assignments, then, which Go compiles to a branch, as it does every float `if`: it makes no select of a float. (Selecting the values' bits instead would make no branch, at the cost of moves between the float and the integer registers on each step of a reduction.)

`test/go/programs/selects.goose` (and its `--debug` twin) checks each choice through both backends at every scalar type, at the ends of each range, with NaNs and signed zeros, into every kind of destination, and next to what stays a branch; `test/go/export/selects/` compares the choices of export fns with Go's, and `run_go_tests.py` reads the code Go makes of each for arm64 and amd64 at -O2 and -O0: a select, and no conditional branch but those of its loop and its guard (`Runner.select_asm`). On an arm64 Neoverse N1 with Go 1.24, `o[i] = max(a[i], b[i])` over 4096 `i64`s takes 4.2 µs on random data as on sorted (`BenchmarkMaxPairsRandom`, `BenchmarkMaxPairsSorted`), where its branches took 12.9 µs and 5.9 µs; `s += clamp(x, 250, 750)` takes 4.7 µs either way, where it took 11.9 µs and 6.2 µs; clamping 4096 random bytes in place 5.2 µs, where it took 10.4 µs; and the max-reduction `m = max(m, x)`, which was a select already, 3.3 µs.

The kernels of issue #26 also kept bounds checks their indices made unnecessary, in gaps of the front end's bounds-check elimination that both backends share: a fact an inlined body states is lost after the body where it returns early, or where it cannot complete; and a loop bounded by its trailing `if c { break; }`, rather than by its condition, keeps every check that bound would remove. `test/go/bce_gaps/` holds a minimal reproducer of each, which `run_go_tests.py` checks with `--bce-test` (`Runner.bce_gaps`), and its README.md writes them up, with their causes in `bce.h`, for upstream.

## 4. Using the Go Backend

The command line is in [`docs/command_line.md` §15](docs/command_line.md#15-writing-go---targetgo); in short:

| Command | What it does |
|---|---|
| `goose --target=go -o out.go prog.goose` (or `goose -o out.go prog.goose`) | Writes one Go source file holding the program and the runtime it uses (§2), `package main`, which `go build out.go` builds with nothing but Go's standard library and `CGO_ENABLED=0`, laid out as `gofmt` lays it out (§3.7). |
| `goose run --target=go prog.goose [-- args]` | Writes the Go to the program's build directory under `GOOSE_HOME` (as `main.go`), builds it with `go build` and runs it, exiting with its exit code. `goose --target=go prog.goose` does the same. |
| `goose build --target=go prog.goose [-o exe]` | Builds the executable beside the root file, or where `-o` says. |
| `--go-package name` | The file's package: `main` for a program, `goose` for a library by default. |
| `--library` | A package with no `func main` and no `init`, which the first call of an export fn's entry point starts (§3.5): the globals, initialized on a block of its own. Importing it does nothing, and nothing it runs exits the process. A `fn main()` the program has is not run. A file with `export fn`s and no `fn main()` is a library without it. |
| `--frame-reserve size` | The address space each block reserves for its fixed-frame stack (§3.6), from 64 KB: 1 GB by default, 64 MB for a library. Go alone has one. |
| `--include helper.go` | Go source spliced into the file for the `extern fn`s the program calls (§3.5): its package clause and build constraints dropped, its imports merged, its lines kept (`//line helper.go:N` before each run of lines). A C header is refused. |
| `--go-build expr` | Starts the file with the build constraint `//go:build expr` (§3.7), which `go build` honors as it builds the file's package: `--go-build goose_x` makes a file built with `-tags goose_x` only. For the Go `-o` writes; `goose run` and `goose build` refuse it. |
| `--debug`, `--stack-reserve`, `-DGS_STACK_RESERVE`, `-DGS_STACK_GAP` | As for C: the checked arithmetic and casts of §3.1, and the size of each data stack's reservation and guard gap (§2.1), which the compiler reads as integer constants and writes into the file (`gsStackReserve`, `gsStackGap`). |

An `export fn name` is two Go entry points (§3.5), named after its symbol with each word capitalized: `Name(args...)`, on a block from the runtime's pool, and `NameWithStack(gs, args...)`, on a `*GsStackBlock` the caller holds. A Go program imports the library's package and calls them:

```go
n := stats.CountWords("the quick brown fox")   // export fn count_words(text: const u8[:]) -> i64
gs := stats.AcquireStackBlock(0)                // or stats.NewStackBlock, and gs.Close()
defer stats.ReleaseStackBlock(gs)
m := stats.MedianWithStack(gs, []int64{9, 1, 7}) // export fn median(xs: i64[:]) -> i64
```

The README has the whole example, and one of `--include`.

## 5. Testing: `test/run_go_tests.py`

`python3 test/run_go_tests.py` checks the Go backend against the C backend. Every program it runs is compiled by both, at `-O2` and, but for the generated overflow and `--fuzz` programs, at `-O0` too, where nothing is inlined and every call stays a call. The Go must pass `go vet` with `CGO_ENABLED=0` (the `unsafeptr` analyzer included) and `gofmt -l`, which must find nothing to change in any file the suite writes (§3.7), build, and run exactly as the C does -- stdout, stderr and exit code -- also when built with `-gcflags=all=-d=checkptr` (at `-O2`), which checks every `unsafe.Pointer` conversion and the arithmetic on one at run time (what `go test -race` turns on, without cgo). Both backends must print the same `--stacks` report, which their shared accounting gives (`src/codegen_stacks.h`), and the runs must print what the expected files hold. Its sections:

| Section | What runs |
|---|---|
| `test/go/programs/` | The Go backend's own programs, one or more per construct and per runtime check, judged against `test/go/expected/` (`<name>.out`, `.stderr`, `.exit`), which `--bless` writes from the C runs. A program that declares the warnings its compile prints, with `// warning:` lines as the C suite's fixtures do, must print exactly those under `goose --check`, for C and for `--target=go` (`Runner.declared_warnings`). `shift_operand_casts.goose` uses this to check, beside the values it prints, that the checker calls no cast that widens a shift's left operand redundant (issue #41). [`docs/upstream/shift-operand-casts.md`](docs/upstream/shift-operand-casts.md) writes that up for upstream, with the warning on the same line that likely looked like such a call. |
| `test/stdlib/`, `test/threads/` | The C suite's fixtures of the standard library and of workers and queues, also with `--debug` where a fixture's first line asks for a `GS_DEBUG` run, with the `-D` it names, each run in a directory of its own, judged against `test/expected/` as `run_tests.py` judges a C run. |
| `samples/` | Every sample but those importing the C-only `gfx`, `ui`, `audio` and `physics` modules: run with `data/<name>.args` and `data/<name>.stdin` in a directory of its own whose `data/` is the samples', the C with its header (`call_c.h`) and the Go with its Go port (`call_c.go`) spliced in by `--include`. Stderr is the samples' timings, compared with every number masked; stdout must be what `samples/expected/` holds. |
| `test/go/export/<name>/` | Libraries of `export fn`s compiled with `--target=go --library` (and the directory's other `.go` files by `--include`), with Go tests that call the entry points: `go vet` and `go test`, also with `-d=checkptr`, including `testing.AllocsPerRun` checks that a call allocates nothing on Go's heap, and calls from many goroutines at once. `lazy/` and `init_abort/` check a library's start from their `TestMain` on: that the import mapped nothing (`gsMaps`), set no fault handling and ran no initializer, that every call leaves its caller's fault setting as it found it, and that an abort, `exit()` and a start that aborts are panics with a `*GsError`. |
| The code of `test/go/export/wide/` | The wide loads and stores of §3.8 (issue #23): the library compiled at -O2 and -O0 and by Go for arm64 and for amd64 (`go build -gcflags=-S`, which cross-compiles with nothing but the toolchain); each export fn an `// asm:` line annotates must reach memory through a pointer as it says, `load n` with one n-byte load, `store n` with one n-byte store, `none` never at all, as a local array on Go's own stack does (`Runner.wide_asm`). |
| The code of `test/go/export/selects/` | The selects of §3.9 (issue #26), compiled the same way: each export fn an `// asm: select, branches m` line annotates must have a conditional select (`CSEL` and its kin on arm64, `CMOV` on amd64) and exactly m conditional branches, those of its loop and its guard, so that no choice it makes is a branch (`Runner.select_asm`). |
| `test/go/bce_gaps/` | The reproducers of the front end's bounds-check elimination gaps issue #26 found (§3.9): `goose --check --bce-test` at -O1 and -O2 must verify each `// bce:keep` and `// bce:elide` line, so that the write-up beside them says what BCE does (`Runner.bce_gaps`). |
| The Go of `test/go/export/inline_refs/` | Locals handed to inlined functions by reference (issue #24, §3.6): the library compiled at -O2, each export fn a `// frame:` line annotates must take as many slots on the fixed-frame stack as it names, `none` none at all (`Runner.frames`), the locals whose address outlives an inlined body alone in the frame; its Go tests check each export fn against the same written in Go and benchmark the parser-shaped scan against it. |
| `test/go/build_only/`, overflow, `test/go/unsupported/`, the command line | Programs that never end, only built; data stack overflow at a 64 KB reservation; programs using what this version refuses, which must name it; `-o out.go`, `--go-package`, `--library` (a host importing a library, which starts at its first call), `--frame-reserve`, `--include` (the lines an error, `runtime.Caller` and a panic's frame name in it), `--go-build` (`go build` skipping the file without the tag and building it with it), `goose run` and `goose build --target=go`. |
| `--sweep` | Every program of the C suite's other categories (`test/codegen/`, `test/lifetimes/`, `test/optimizer/`, `test/runtime/`, `test/storage/`, `test/syntax/`, `test/typing/`) through the checks of the `test/stdlib/` section. One the Go backend refuses as not supported yet, at a level or at all, is counted, not failed, and so is one that differs by design (`SWEEP_KNOWN`: a recursion that exhausts the native stack is an abort in C and a fatal error of the Go runtime). |
| `--fuzz N`, `--fuzz-flow N`, `--fuzz-values N` | Random programs of scalar arithmetic and conversions, of control flow, and of fixed-size values, which both backends must run alike. |

`-j N` runs N checks at once, `-v` prints each one, `--workdir` names where the generated files go (`build/go-tests` by default), `--jit-reference` takes the C reference from TinyCC in the compiler's process, and names run only those programs. [`docs/testing.md`](docs/testing.md#the-go-backends-suite) has the details. The runtime's own tests are `cd runtime/go && CGO_ENABLED=0 go vet ./... && go test -race ./...` (the race detector needs cgo on Linux; `CGO_ENABLED=0 go test -gcflags=all=-d=checkptr ./...` runs the pointer checks without it).
